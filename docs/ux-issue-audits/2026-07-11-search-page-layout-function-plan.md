# 2026-07-11 搜索页布局优化与功能完善计划

## 背景

本计划针对当前搜索页截图和仓库中的搜索页实现，目标不是把控件重新摆一遍，而是修正搜索页的任务模型、范围模型、筛选模型、结果模型和后端能力说明。

当前页面已经比 2026-06-13 的早期审计有所进步：搜索内容有可见标签，搜索结果支持分页、命中高亮、导出入口、取消搜索、隐私模式和跳回会话上下文。但截图中的体验问题仍然成立，核心原因是页面把多个状态模型同时展示给用户：

- `WorkspaceScopeController` 同时展示摘要、已生效 chip、内联按钮和抽屉入口。
- 范围、消息类型和高级筛选分属不同清除体系。
- 日期、会话范围、消息类型会影响后端请求；排序和分组只整理已加载结果；发送者、收藏、附件只显示为暂不支持。
- 日期输入只限制键盘和正则格式，不负责引导输入、自动跳格、字段级错误或真实日期合法性。

## Grilling 结论

### 已确认设计约束

- 搜索页的基础定位是克制的本地工具台，不是彩色筛选面板。
- 视觉必须贴近当前 chatlogUI 风格：低饱和、少装饰、少状态色，蓝色只服务于主操作和当前选择，灰色服务于结构和层级。
- 默认任务路径是关键词搜索优先，入口上下文用于强化“全部会话 / 当前会话”，不能抢走关键词输入和结果阅读的主导权。
- 高级筛选不默认铺开。当前后端没有除范围、类型、日期之外的可操作筛选，因此现阶段直接移除空的“更多筛选”入口；新增真实能力后再引入轻量 popover/sheet。
- 日期输入是一个整体控件，不是三个独立小方框；每个日期只使用一个真实输入值，视觉上投影为 `____ - __ - __` 三段横线。
- 日期主路径是连续数字输入，用户可输入或粘贴 `20260711` 并归一为 `2026-07-11`；辅助路径是日历按钮和快捷日期点击。
- HTML 静态设计稿和 Playwright 截图必须随设计迭代更新，不能只停留在文字计划。

### 2026-07-11 Grilling 纠偏记录

- 上一版 `output/search-page-grilling-redesign.html` 的方向不应作为最终视觉基准：绿色/橙色状态 chip、较强的状态色和厚重抽屉不符合当前 chatlogUI 的低饱和蓝灰工具风格。
- 下一版 HTML 设计稿必须复用当前应用的视觉语义：`--surface-base`、`--surface-raised`、`--surface-subtle`、`--border-subtle`、`--text-secondary`、`--accent`、`--radius-md`、`--space-*`。除错误和警告外，不新增大面积彩色状态。
- 当前代码结构决定改造不能只画页面：`SearchView` 现在组合 `WorkspaceScopeController`、`GlobalSearch`、`SearchAdvancedFilters`、`SearchResults`；日期控件来自通用 `DateInput`，且被媒体、统计、图谱、导出等页面复用。搜索页应新增或局部引入搜索专用日期范围控件，避免粗暴替换全局 `DateInput`。
- 范围、类型、日期都属于同一层级的搜索条件。它们不应被拆成多个纵向区域；下一版设计应优先探索一条紧凑搜索条件栏，让条件自然换行，而不是人为分成“范围行 / 类型行 / 日期行”。
- 主页面可以直接展示日期，但必须是轻量横线式整体输入，不能恢复成两个普通大输入框，也不能重新制造一个默认展开的高级筛选面板。
- 每次形成一组稳定设计决策后，必须同步更新 HTML 静态稿，并用 Playwright 输出桌面、窄屏和关键交互截图。

### 2026-07-12 首轮原型证据（已替代）

- 7 月 12 日原型只证明了紧凑条件栏和草稿/已应用状态的初步方向；其中单选类型、20 条批次、静态日历、双提交动作和按钮式结果行均已被后续 Grilling 决策否定。
- `search-minimal-*` 截图保留为过程证据，不再作为目标布局、控件或计数文案的验收基准。

### 2026-07-13 Grilling 收口与最终原型证据

- 关键词、范围、类型、日期和发送者组成统一草稿。页面只有一个稳定提交位置：关键词变化时为“搜索”，只有筛选变化时为“应用筛选”；修改草稿不替换 last-known-good 结果。
- 范围统一为“全部 / 当前 / 指定会话”互斥模型；消息类型改为九类紧凑多选；发送者位于“更多筛选”，不再用永久 chip 或第二套清除入口。
- 桌面端关键词一层、范围/类型/更多/日期一层。390px 草稿态固定为“范围/类型/更多/取消”一层、日期一层，条件区高 140px，不出现第三层筛选。
- 日期仍是一个连续输入控件：每个日期由 `4/2/2` 三段下划线呈现；连续输入 8 位完成一个日期，向开始日期粘贴 16 位可一次填完起止日期。辅助入口只保留今天、最近 7 天、最近 30 天、本月至今和真实可换月日历。
- 结果改为连续、无卡片按钮的语义行；保留会话、发送者、产品消息分类、时间、后端命中片段、命中来源和固定媒体槽。整行打开上下文，文本仍可选择复制。
- 结果工具条通过一个无边框菜单切换手动累积、自动累积和替换分页；普通请求统一 50 条。分页返回累积时保留已有区间并显示中间缺口，本地整理时改为覆盖范围提示。
- 导出面板保留“全部命中”和“当前已加载/当前页”，每次打开默认全部命中；全量明确使用后端基线顺序，部分导出冻结当前排序与分组。
- 静态原型：`output/search-page-grilling-redesign.html`。它使用合成消息，不依赖 sidecar 或真实聊天数据，也不代表真实 React/sidecar 已实现。
- 最终截图：`search-v2-desktop.png`、`search-v2-filter-draft.png`、`search-v2-date-popover.png`、`search-v2-narrow.png`、`search-v2-narrow-draft.png`、`search-v2-export.png` 和 `search-v2-gap-detail.png`，均位于 `output/playwright/`。
- Playwright 实测：1440x900 默认条件区高 115px，首条结果 y=274.3；390x844 草稿条件区高 140px，结果区 y=261.6，首条结果 y=361.4；390px 与 320px 均满足 `scrollWidth === clientWidth`。
- Axe 在默认、类型菜单、发送者菜单、日期弹层、最近搜索、导出、内联缺口、覆盖提示、390px 默认和 390px 草稿状态均为 0 违规；最终控制台为 0 error、0 warning。
- 浏览器断言覆盖范围双向切换、指定会话空选择阻断、类型多选、16 位日期粘贴、反向日期范围、pending 取消、历史填入不提交、浏览方式记忆、分页回累积缺口、导出默认值及分层 Escape，全部通过。

### 2026-07-12 第二次 Grilling 纠偏

- 上一版虽然压缩了布局，但把菜单、快捷日期、导出、上下文和翻页都做成有边框按钮，形成“边框容器套边框控件”的重复层级。该视觉稿不再作为按钮设计基准。
- “少就是多”是整页原则，不只针对日期：普通命令默认无边框，hover/focus/selected 时才出现轻背景或焦点环；实心蓝色只保留给搜索主操作。
- “应用筛选”已确认不是装饰按钮。L2 必须拆分 `draftFilters` 与 `appliedFilters`；范围、类型和日期只修改草稿，搜索或应用后才生成新的请求快照。
- 原计划的章节虽然提到了结果和后端，但视觉原型与说明重心偏向日期。修订版必须以功能实现、布局优化、UI 体系、元素设计四条主线组织，日期只是元素设计中的一个子项。

### 2026-07-12 第三次 Grilling：剩余问题审计

这次审计重新区分了“真实 React 页面”和“已确认 HTML 原型”。结论不是原有问题已经被原型解决，而是目标方向已经明确、正式实现仍未开始，并且代码与原型中还存在以下高风险缺口。

#### P0：会让搜索范围、结果或状态不可信

| 问题 | 当前证据 | 必须达到的结果 |
| --- | --- | --- |
| “全部会话 / 全部命中”目前并不保证完整 | sidecar `handleSearchCompat()` 在未传 chats 时只读取前 300 个会话；普通关键词路径还会先按会话截取有限候选消息，再在候选集的 `PlainTextContent()` 上匹配，`total_count` 因而可能只是候选集命中数 | 普通关键词搜索必须有可验证的完整范围、稳定分页和真实总数；完成前 UI 不得宣称“全部命中”，全量导出也不得把候选集当全集 |
| “文件”类型会返回非文件消息 | 前端把 file 映射为 `msg_type=49`；sidecar 49 是 Share 大类，文件只是 `sub_type=6`，链接、小程序、引用、转发、笔记等也会通过当前过滤 | 建立共享的用户类型 taxonomy 和 type/subtype 精确映射；文件筛选只返回真实文件，并用每类合成消息验证总数与结果 |
| 当前会话可能静默退化为全部会话 | `resolveSearchScopeChat()` 在 `scope=current` 但找不到 route chat 或已选会话时返回 `null`；`createSearchRequest()` 随后省略 `chats`，请求实际变成全局搜索 | 当前会话不可解析时阻止搜索并给出选择会话的恢复动作，绝不静默扩大范围 |
| 本地排序/分组可能取消请求并留下永久 loading | `changeAdvancedFilters()` 无论后端条件是否变化都会先 `cancelActiveRequest()`；只改 `sortMode/groupMode` 时不重启请求，旧请求又因 request id 失效而不会收尾 loading | 排序/分组完全从后端请求状态分离，不取消搜索或加载更多，也不改变 request status |
| “清除筛选”执行了错误动作 | `SearchResultsPane.handleEmptyAction()` 把 `clear-filters` 绑定到 `onClearSearch()`；store 的 `clear()` 清掉关键词和结果，却保留范围、类型和日期 | 清除筛选只重置统一筛选草稿；清除关键词、清除筛选、重新搜索是三个明确动作 |
| 加载更多失败会抹掉已有结果 | `loadMoreResults()` 失败调用全局 `setError()`；结果组件见到 error 后整页只显示错误态 | 已有结果保持可读，只在列表尾部显示“加载失败 / 重试”，初次搜索错误才使用整页错误态 |
| 日期可能代表错误的一天 | 当前只验证 `YYYY-MM-DD` 形状，不验证真实日期；`Date.UTC` 又把用户的本地自然日按 UTC 边界解释 | 统一验证真实日期、闰年和起止顺序，并明确按用户本地时区还是数据源时区生成 `since/until`；用边界消息做合成测试 |
| 就绪状态被假定为成功 | 搜索空态把 service/http/db readiness 硬编码为 `true`，搜索错误又统一翻译为“检查网络连接” | 区分服务未启动、HTTP 未就绪、数据库未就绪、超时、参数错误、取消和未知响应，并提供对应恢复入口 |

#### P1：主路径可用，但会让用户迷失或重复操作

| 问题 | 当前证据 | 规划要求 |
| --- | --- | --- |
| 全部会话结果看不出来自哪里 | flat 结果行只渲染 sender、time、content；没有稳定显示会话名，且 presenter 优先使用原始 `sender` 而不是适配层已有的 `senderName` | 每行固定显示会话名、可读发送者、消息类型、时间和命中片段；隐私模式保持同样结构 |
| 图片、视频和文件结果可能是空白或原始结构文本 | snippet 只读取 `message.content`，不读取 `fileName`、附件摘要、媒体类型或安全占位 | 各消息类型有专用摘要策略；文件优先安全文件名，媒体显示类型/说明，不把 XML、本机路径或空字符串当正文 |
| 命中高亮可能与后端匹配不一致 | 前端只高亮完整关键词的大小写不敏感连续子串；后端若分词、匹配元数据或多个词，结果行可能没有任何可见命中 | 先证明后端匹配语义，再共享分词/高亮规则；无法定位正文命中时明确显示“匹配到文件名/元数据”等来源 |
| 中文输入法可能被 Enter 提前提交 | 搜索框 keydown 没有检查 `isComposing`；当前输入变化还会触发 300ms 自动搜索 | 取消输入即搜；IME 组合期间 Enter 只完成上屏，不提交搜索，组合结束后再允许 Enter/按钮执行 |
| Esc 的后果过大 | 当前搜索框按 Esc 直接清空关键词和结果 | Esc 先关闭建议/菜单；没有浮层时只清输入草稿，不应无提示抹掉稳定结果 |
| 结果打开可能重复触发 | 结果使用原生 button，同时在 `onKeyDown(Enter)` 和 `onClick` 调用打开逻辑；浏览器原生 Enter 还会生成 click | 只保留原生 click 激活路径，并补键盘集成测试，确保一次按键只加载一次会话 |
| 打开全部会话命中依赖前端会话列表完整 | `resolveSearchHitNavigation()` 要求命中的 chat 已存在于 `chat.conversations`，否则搜索结果整页进入错误态 | 允许按后端 chat id 直接补齐/解析会话；失败应保留结果并在该行提供刷新会话或重试 |
| 关键词和历史没有长度/规范边界 | 搜索只检查 trim 非空；最近搜索把原始关键词存入 localStorage，最多限制条数，不限制单条长度 | 定义 Unicode/空白归一、最大长度、超长错误和历史截断；明确本地明文搜索历史的默认开关与清除策略 |
| 请求分页可能因去重或数据变化漂移 | next offset 使用去重后的 `messages.length`；数据库在分页期间变化时可能重复、遗漏或循环 | 独立保存服务端 next offset/query window；检测重复 ID、总数变化和空页；全量导出使用冻结的 applied snapshot |
| 返回上下文没有完整恢复契约 | return snapshot 只声明关键词、类型、范围和 scope chat，没有日期、指定会话、排序/分组、已加载位置和滚动位置 | 即时返回至少恢复 applied query、已加载集合、active result 和滚动位置；重载恢复能力另行明确，不能含私密 URL 参数 |

#### P2：布局、UI 和元素仍需收口

- 当前真实页面同时存在大范围卡片、常驻最近搜索、默认展开高级筛选、结果命中导航条和结果卡片，首屏仍有重复层级；已确认原型尚未落入 React。
- 当前结果标题、输入下方计数和结果面板计数重复表达数量；目标只在结果工具条保留一份可信的 applied summary。
- `上一条命中 / 下一条命中` 单独占一整行，与列表键盘导航、加载更多或分页形成第二套导航；目标应只保留一种列表推进模型。
- 范围应建模为互斥联合：`全部会话 | 当前会话(chatId) | 指定会话(chatIds)`。不能把当前会话与 selected chats 合并成一个 `chats` 并集，否则“当前”可能扩大范围。
- 日期原型把真实 input 设为透明，焦点时没有可见光标或当前段提示；输入六位时所有段立即变红，也把“尚未输完”误判成“犯错”。输入中应保持中性，只有不可能的前缀、失焦或尝试应用时显示错误，并用活动下划线/光标提示编辑位置。
- 原型的日历上一月/下一月按钮目前没有改变月份；范围/类型菜单也没有实现 Arrow Up/Down 导航，不能把静态可点外观当成完成的交互。
- 原型结果整行出现 hover 背景，但实际只有尾部箭头按钮可点击，视觉暗示与点击范围不一致。
- 原型与正式实现对结果推进方式曾互相矛盾：旧 HTML 使用替换分页，现有 React 使用累积“加载更多”。最终 HTML 已通过一个统一入口展示三种模式；真实 React 仍待按同一状态模型实施。
- 2026-07-12 axe 实测在默认、日期和窄屏状态均发现 6 个日期占位文字对比度问题（3.64:1）；导出对话框还因页面 footer 与 dialog footer 重复产生 contentinfo landmark 问题。
- 深色模式、200% 缩放、长会话名、超长中英文混排、系统消息和未知消息类型仍缺少原型截图证据。

#### 新增实施约束

- `SearchAppliedRequest` 必须包含关键词、互斥范围、消息类型、已校验日期及其时区解释、后端分页游标/窗口；`SearchDraft` 只负责编辑，不参与结果说明、加载更多和导出。
- 初次搜索、重新应用、加载更多和全量导出使用不同但可关联的状态，不复用一个 `loading/error` 布尔值覆盖所有界面。
- 结果展示模型优先使用适配后的可读名称和类型专用摘要，不让 L3 自行猜测原始字段。
- 最近搜索是否持久化属于隐私产品决策，不能因为 localStorage 可用就默认等同于用户同意。
- HTML 原型已补齐三种结果浏览模式及其切换入口，并修正日期编辑反馈、日历月份导航、结果行点击语义、弹层关闭和 axe 问题；桌面与窄屏证据已于 2026-07-13 重拍。真实实现仍需完成等价键盘与集成测试。

#### 已确认：三种结果浏览模式

| 模式 | 默认与行为 | 数据状态 | 失败与停止 |
| --- | --- | --- | --- |
| 手动累积加载 | 默认模式；列表尾部显示 `加载更多 50 条` | 新页合并到已加载集合，保留阅读位置；已加载数持续增长 | 失败只出现在列表尾部，可重试；用户决定何时继续请求 |
| 自动无限加载 | 用户主动切换后，接近列表尾部时自动请求下一批，增量批次不少于 50 条 | 与手动模式共享累积集合、去重、服务端 offset 和虚拟列表 | 首次失败后停止自动触发，显示重试；同时保留可键盘触发的加载入口，不制造无法停止的请求循环 |
| 替换式分页 | 用户主动切换后，每次只显示一个后端页面；支持上一页、下一页和可达页跳转 | 当前页替换上一页，内存和 DOM 保持稳定；保存 page/offset 用于返回定位 | 页面请求失败时保留旧页并显示页级重试，不清空列表 |

共同规则：

- 三种模式使用同一份 `appliedRequest`、统一的 50 条普通请求大小、同一 `totalCount` 和同一后端排序基线；切换模式不会应用筛选草稿，也不会改变搜索条件。
- 手动累积与自动无限加载只是触发策略不同，可以无损切换并复用已加载集合。
- 替换式分页是不同的数据窗口。进入、离开分页模式时必须有确定的页码、active result、滚动位置和本地排序/分组规则，不能简单复用累积模式的 `messages.length`。
- “当前已加载”导出随模式使用准确名称和数量：累积模式为当前累积集合；分页模式必须明确为“当前页 n 条”，不能继续用容易误解的泛称。
- 全部命中导出始终使用 applied snapshot 建立独立全量任务，不受浏览模式、当前页或 DOM 中可见行影响。
- 切换入口位于结果工具条的单个无边框“浏览方式”菜单中，不增加三个并排按钮；菜单项显示当前选择、简短行为说明和可访问选中状态。
- 浏览模式不是搜索筛选，不显示“应用筛选”；切换后立即改变结果浏览策略。
- 自动无限加载必须结合虚拟列表和显式状态公告；不得因为 sentinel 在错误态或空页后仍可见而无限重试。

#### 已确认：进入替换式分页时保留阅读位置

- 从手动累积或自动无限模式切换到替换式分页时，优先定位当前 `activeResultId` 对应的后端页。
- 没有 active result 时，定位虚拟列表中首个可见结果对应的后端页；两者都无法解析时才回到第 1 页。
- 每条搜索结果除业务 id 外还要保存不可被本地展示操作改写的 `sourceOffset` 与 `sourceIndex`。`sourceIndex = response.offset + indexInResponse`，目标页由 `floor(sourceIndex / pageSize) + 1` 计算。
- 本地升降序、按会话/日期分组、去重、虚拟化和 DOM 重排只改变 view model，不改变 `sourceIndex`。
- 切换到目标页后继续保持同一 active result；焦点移动到该行，但只有在该行不在可视区域时才进行最小必要滚动，避免页面跳动。
- 若数据库变化导致目标页不再包含该结果，分页视图保留目标页并显示非阻塞提示，再按消息业务 id 在相邻页做有限查找；不能静默把 active result 指向另一条消息。
- 该定位规则必须使用 applied request 的后端排序基线。本地排序后的视觉位置不能被误当成后端页码。

#### 已确认：从分页返回双向累积窗口

- 从替换式分页切回手动累积或自动无限模式时，以当前页为锚点建立双向累积窗口，不自动补抓第 1 页到当前页之间的所有数据。
- 当前页、active result、键盘焦点和可视位置保持不变；切换本身不发送请求，只有用户触发边界操作或无限模式的边界 sentinel 进入阈值后才请求相邻页。
- 手动模式在窗口顶部显示 `加载前 50 条`，底部显示 `加载更多 50 条`；距离边界不足 50 条时显示真实剩余数，相应方向已经到达数据边界时隐藏该命令。
- 自动无限模式使用上下两个 sentinel：接近顶部加载前一批，接近底部加载后一批。每个方向有独立 pending/error/retry 状态，任何失败都会停止该方向的自动触发，不能形成重试循环。
- 累积状态不能再用单个 `offset + messages.length` 表达。L2 至少维护 `loadedRanges`、`minSourceIndex`、`maxSourceIndex`、`hasPrevious`、`hasNext`、两个方向的 request id/status 以及 active result。
- 相邻响应按 `sourceIndex` 合并；消息业务 id 只负责重复检测，不能因为去重后数组变短而改写后续后端 offset。
- 结果摘要同时表达数量与位置，例如 `已加载 50 / 共 132 条 · 当前窗口第 51–100 条`。存在非连续缓存时显示多个已加载区间或明确“中间尚未加载”，不能把缺口伪装成连续数据。
- 若已有累积缓存且包含当前 active result，恢复该缓存和之前的滚动锚点；没有可用缓存时才以当前分页页作为新窗口。缓存存在但不包含当前页时，仍必须优先保留当前阅读位置，具体缺口合并策略在实现前用状态测试固定。
- 本地排序和分组只整理当前已加载窗口；顶部/底部加载依据永远使用后端 `sourceIndex` 边界，而不是整理后的第一行或最后一行。
- 分页模式切换到无限模式不会自动开始连续抓取；只有用户实际滚动接近某一边界时才加载，避免模式切换本身制造大量请求。

#### 已确认：记住用户最后选择的浏览方式

- 首次使用搜索页时默认 `manual`（手动累积加载）；用户主动切换为 `infinite` 或 `paged` 后，将最后选择保存为本机非敏感偏好。
- 浏览方式跨关键词搜索、筛选应用、离开/返回搜索页和应用重启保留。新搜索只清空旧结果、页码、加载区间、active result 和滚动位置，不改写浏览方式偏好。
- 浏览方式偏好不包含关键词、会话 id、日期或结果内容，隐私模式无需清除；持久化失败时静默回退到当前会话内状态，不影响搜索。
- 偏好值必须经过白名单校验，只接受 `manual | infinite | paged`；未知、损坏或旧版本值回退到 `manual`。
- “浏览方式”菜单显示当前选择，并提供 `恢复默认方式`。恢复默认只把偏好改回手动加载，不改变当前 applied query；若当前结果已存在，则立即切换为手动模式并保留可恢复的阅读位置。
- 模式持久化属于 `useSearchPreferenceStore` 一类的本地展示偏好，不进入搜索请求、URL、诊断日志或业务导出。
- 自动无限模式被记住后，新搜索首屏只请求第一批；不会因为偏好是 infinite 就在用户尚未滚动时连续抓取后续页面。首批大小仍需与 50 条增量规则一起确认。

#### 已确认：保留非连续缓存并显式展示缺口

- 若旧累积缓存与当前分页页不相邻，返回累积模式时同时保留旧缓存和当前锚点页，不丢弃已经完成的请求。
- 各 `loadedRange` 按后端 `sourceIndex` 排列；相邻区间合并，非相邻区间之间渲染一条真实 gap row，例如 `中间 80 条尚未加载`。
- gap row 不是普通搜索结果，不参与关键词高亮、结果计数、键盘命中导航或业务导出；它只表达数据缺口和提供相邻补载入口。
- 缺口两侧分别按至少 50 条向中间扩展；不足 50 条时一次加载剩余缺口。自动无限模式接近 gap row 时也只抓取相邻一批，不一次性填满整个缺口。
- active result 所在区间优先保留在虚拟列表可视窗口内。插入旧缓存、gap row 或新批次时，用 source anchor 修正 scroll offset，避免内容插入导致阅读位置跳动。
- 新关键词、重新应用筛选或 applied request 失效时清空全部区间和缺口；单纯切换浏览方式、排序或分组不清空缓存。
- 若命中规模超过实测内存预算，缓存淘汰必须以完整 range 为单位、优先淘汰距离 active result 最远的区间，并把被淘汰位置重新表示为 gap；不能悄悄减少“已加载”数量。

#### 已确认：普通搜索统一为 50 条

- `SEARCH_PAGE_SIZE` 的目标值由当前 20 调整为 50。首次搜索、替换式分页、手动向前/向后加载、无限滚动和缺口补载均使用同一个 50 条请求大小。
- 最后一页、数据起点或缺口剩余量不足 50 时，请求/显示真实剩余数量；按钮文案不能承诺不存在的 50 条，例如显示 `加载剩余 32 条`。
- 不在主页面增加每页数量选择器。统一大小降低用户决策、页码换算、source index、缓存区间和模式切换的复杂度。
- 页面结果请求固定 50 不代表全量导出也按 50。全部命中导出可在合成性能测试后使用独立内部批次，例如每次 500 条，并继续遵守快照、取消、重试和内存阈值。
- 50 条必须通过真实 sidecar 合成测试验证首批响应、序列化、适配和首屏渲染时间；列表使用虚拟化，不能因为 DOM 行数增长而把请求大小重新降回 20。
- 现有 React 常量和相关测试仍使用/展示 20 条，属于待实施项。2026-07-13 HTML 原型及新截图已统一为 50 条；旧 `search-minimal-*` 截图不再证明目标计数文案。

#### 已确认：缺口随结果整理方式切换表达位置

- 当结果保持后端基线顺序时，gap row 位于两个 `loadedRange` 之间，用户可以直接理解它对应哪一段尚未加载的数据。
- 一旦启用本地排序或分组，后端 source index 与视觉行位置不再一一对应；此时从结果列表中移除 gap row，不能把缺口错误归入某个日期或会话分组。
- 排序/分组状态下，在结果工具条下方显示一条紧凑 coverage row，例如 `已加载第 1–150、401–450 条 · 中间 250 条未加载`，并提供 `加载相邻 50 条`。
- coverage row 使用普通文字、分隔符和无边框命令，不使用卡片、彩色状态条或多个范围 chip。它属于结果完整性说明，不与筛选草稿混合。
- coverage row 的已加载区间按后端 source index 表达，不按本地升序、会话组或日期组重新编号。排序/分组标签继续明确 `仅整理已加载结果`。
- 存在多个缺口时，默认动作补载距离 active result 最近的缺口；其他缺口通过同一行的轻量菜单选择，不能铺开多个常驻按钮。
- 用户恢复后端基线顺序时，coverage row 收回，gap row 回到对应区间之间；这个切换只改变 view model，不请求后端、不丢缓存、不移动 active result。
- gap row 与 coverage row 都不计入搜索结果数量、键盘命中序号或导出记录数，但其状态变化需要通过礼貌的 live region 公告，避免每次滚动反复播报。

#### 已确认：“当前已加载”导出覆盖全部缓存区间

- 手动累积和自动无限模式中的“当前已加载”指当前搜索快照下、仍保留在所有 `loadedRange` 中的唯一结果合集；区间不连续时仍全部导出。例如已缓存第 1–150、401–450 条时，导出 200 条，而不是只导出 active result 所在区间。
- 导出计数按仍保留的唯一消息记录计算，不按最小/最大 `sourceIndex` 的跨度计算。gap row、coverage row、已淘汰记录、正在请求或请求失败但未写入缓存的记录均不计入，也不能出现在业务导出文件中。
- 导出面板需要如实显示 `当前已加载 200 条`，并在存在缺口时补充 `包含 2 个已加载区间，中间 250 条尚未加载`；不能用一个“已加载 200 / 450”暗示缓存是连续的。
- 替换式分页不使用含混的“当前已加载”，而显示 `当前页 50 条`（末页显示实际条数），且只导出当前页窗口。切回累积模式后，才重新按全部保留区间计算。
- 当前范围导出在用户确认时冻结一份缓存快照；随后继续加载、补缺口、切换页或发生区间淘汰，不追改已经开始的导出任务。
- 文件元数据至少记录 applied query 摘要、导出模式、已加载区间、未加载缺口、导出记录数和 `partial: true`，使接收者不会把非连续的部分结果误认为完整结果；隐私模式与脱敏规则继续适用。
- “全部命中”仍是每次打开导出面板时的默认项，并基于 applied request 独立抓取完整结果；它不复用页面缓存，也不因当前存在缺口而退化为“当前已加载”。

#### 已确认：部分导出遵循当前视图，全部命中保持后端基线顺序

- 手动累积、自动无限模式的“当前已加载”以及替换式分页的“当前页”，都按用户点击导出时正在查看的本地排序和分组生成文件。导出任务冻结 presentation snapshot，之后切换排序、分组或 active result 不改变已启动任务。
- 未启用本地整理时，部分导出按不可变 `sourceIndex` 的后端基线顺序输出。启用时间升/降序时，文件行顺序与当前结果视图一致；稳定排序使用 `sourceIndex` 作为同时间戳记录的最终 tie-breaker，避免同一快照多次导出顺序漂移。
- Markdown 可使用轻量分组标题保持当前阅读结构；CSV/JSON 不插入伪消息行，而使用独立的 `groupKey` / `groupLabel` 字段及确定的行顺序表达分组。任何格式都保留可追溯的 `sourceIndex` 或等价来源位置元数据，但不把 gap row 导出为业务记录。
- “全部命中”不继承标注为“仅整理已加载结果”的本地排序和分组，始终按后端搜索基线顺序导出。导出面板摘要需要说明 `全部命中将按搜索结果原始顺序导出`，防止用户从当前局部视图错误推断全量文件也会被同样整理。
- 若未来需要“全量后再统一排序/分组”，它应作为单独的后端能力与内存/外部排序方案立项，不能在当前局部整理控件下悄悄扩大语义。
- 当前实现把原始 `search.results.messages` 直接交给 `createSearchExportArtifact()`，没有使用 `searchResultsPresentation.orderedMessages`，也没有分组元数据；正式实现必须在 L2 构建独立的导出 presentation snapshot，而不是让导出器读取 UI 或 DOM。

#### 已确认：日期按本机自然日解释

- 搜索日期与结果行的本机时间显示保持一致。用户选择 `2026-01-02` 时，含义是当前系统时区中的 1 月 2 日，而不是 UTC 的 1 月 2 日；主页面不增加常驻时区选择器。
- 开始边界为开始日期本地 `00:00:00`。结束边界按“结束日期的下一日本地零点减 1 秒”生成，以覆盖完整自然日并正确处理存在夏令时切换的系统时区，不能简单给开始时间加固定 86,399 秒。
- 日期解析必须验证真实公历日期、月份天数、闰年以及开始不晚于结束。输入尚未完成时保持编辑态，不立即显示错误；在字段失焦、按 Enter、点击搜索或应用筛选时才提交校验结果。
- `SearchDraft` 保留日期字符串；用户执行搜索或应用筛选时，`SearchAppliedRequest` 同时冻结解析后的 `since`、`until`、IANA 时区标识（可获得时）及当时的 UTC offset。结果存在期间系统时区变化不能悄悄改写已应用请求。
- 结果摘要只显示用户可理解的自然日期；导出和诊断元数据记录所用时区与实际 epoch 边界。不得把时区标识写成新的视觉 chip，也不得记录任何私密消息内容。
- 当前 `parseDateStart()` / `parseDateEnd()` 使用 `Date.UTC`，而结果行使用 `toLocaleString("zh-CN")`，两者在非 UTC 系统上会错开自然日。正式实现需要改为日历安全的本地边界转换，并增加中国时区、带夏令时地区、闰日、月末和非法日期测试。
- sidecar 的 `since/until` 包含性尚无仓库内权威说明。实现验收必须用恰好位于开始零点、结束日末秒、下一日零点的合成消息验证；若 `until` 实际为排他边界，则 L2 改传下一日零点，但产品层“包含整个结束日期”的语义不变。

#### 已确认：“当前会话”无法解析时失败关闭

- `scope=current` 是请求约束，不是视觉提示。只有解析出经过校验的稳定会话标识后，L2 才能构造并发送搜索请求；不得通过省略 `chats` 参数静默扩大为全部会话。
- 从全局导航进入且没有有效会话上下文时，默认范围仍为“全部会话”，“当前会话”菜单项显示禁用状态与原因。用户不能选中一个实际上无法执行的范围。
- 从会话上下文进入时，优先使用路由携带的稳定会话标识，不以会话列表是否已经加载作为前提。路由标识缺失、非法或已失效且无法解析时，搜索停在可恢复的 scope-resolution error，不发起 `/api/v1/search`。
- 错误提示位于统一条件栏附近：`无法确定当前会话，请选择会话或切换到全部会话`。保留关键词与完整筛选草稿，并提供无边框的“选择会话”和“改为全部会话”操作；不能清空用户输入或自动替用户改范围。
- `SearchAppliedRequest` 中当前会话范围必须表示为带稳定标识的判别联合类型，例如 `all | { kind: current; chatId: string }`，从类型层消除“current 但 chatId 为空”的非法状态。L4 仍只接收已验证的原始参数。
- 诊断仅记录 `scope_resolution_failed`、入口来源和非敏感原因码，不记录会话名、会话 ID、关键词或命中内容。
- 当前 `createSearchRequest()` 只在合并后的 chats 非空时写入参数，因此 `current + null scopeChat` 会形成全局请求。实现时必须在 L2 请求快照创建前阻断，并覆盖全局入口、陈旧路由、会话列表未加载、非法标识和恢复操作测试。

#### 已确认：普通关键词搜索完整性是发布阻断项

- “全部会话”“共 n 条”和“全部命中”是数据真实性承诺。普通关键词搜索必须覆盖 applied scope、类型和日期范围内的全部会话与全部消息，不能保留 300 会话上限，也不能先截取每会话候选窗口再匹配。
- `/api/v1/search` 返回的 `total_count` 必须是真实命中总数；普通页面、三种浏览方式和全部命中导出都基于同一查询定义。前端循环读取当前不完整候选集不构成修复。
- 搜索结果必须采用确定性后端顺序，并以不可变来源位置、游标或数据版本保证同一 applied request 的连续页面不重复、不遗漏。若本地数据库在读取期间变化，必须检测并明确重启/刷新查询，不能继续给出伪稳定的 offset。
- 允许为修复正确性调整 sidecar 内部搜索实现、索引和分页策略；保持 `/api/v1/search` 的普通消息搜索用途与现有基础参数兼容。若稳定查询需要可选 cursor、snapshot revision 或 match metadata，应以向后兼容方式扩展并同步前端契约测试。
- 合成验收至少覆盖超过 300 个会话、单会话消息量超过旧候选窗口、命中位于首尾边界、跨会话同时间戳、数据库中途新增消息、最后一页不足 50、重复本地 ID 和类型/日期组合筛选。
- 完整性能力通过真实 sidecar 验证前，UI 不得显示无条件的“全部命中”；导出对话框中的“全部命中”禁用并就地说明原因，不能静默回退为当前缓存。普通结果摘要使用明确的受限状态，而不是把候选集长度显示成全库总数。
- 该项是 P0 发布门槛。搜索页即使布局、日期控件和交互全部完成，只要完整性测试未通过，就不能按产品级搜索功能验收。

#### 已确认：关键词检索可见消息内容，身份信息使用结构化筛选

- 普通关键词的可搜索语料是用户能够在消息界面理解和核对的内容：文本正文、媒体附言、文件名、链接标题/描述/用户可见 URL、小程序与视频号等卡片标题、地点名称/地址，以及引用、回复、笔记、合并转发中的可见文字。
- 其他结构化消息先经过与展示一致的安全文本提取器再参与索引和匹配。不能把原始 XML、数据库字段拼接或无法在结果行解释的隐藏值当作命中来源。
- 发送者名和会话名不混入普通关键词语料。会话通过范围选择，发送者通过结构化筛选；发送者筛选只有在 `/api/v1/search` 真正支持并通过完整性测试后才进入默认收起的高级筛选，不能继续展示无效占位控件。
- 本机文件路径、内部媒体 URL、MD5、资源 key、消息内部 ID 和其他实现标识不参与普通关键词搜索。用户可见的外部链接 URL 可以搜索，但导出与隐私模式仍按既定脱敏规则处理。
- 图片像素中的文字、语音转写和视频内容不在普通关键词承诺内，除非未来建立明确的本地 OCR/转写索引、来源标记、更新状态和隐私边界；未建立时不能用“搜索全部信息”暗示这些内容可检索。
- sidecar 对每个命中返回稳定的 `matchField`、安全 `matchSnippet`，必要时附结构化消息子项位置。前端只高亮该命中证据，并显示简短来源，如“命中文件名”或“命中引用内容”；不再根据原始 `message.content` 自行猜测命中位置。
- 搜索提取器与消息展示摘要必须共享类型映射测试。文件、链接、位置、引用、合并转发、空媒体和损坏结构数据都要验证“可搜索文本、返回片段、页面摘要”一致，且不泄露内部路径或原始结构。

#### 已确认：普通关键词采用规范化的确定性字面匹配

- 查询词和可搜索消息文本使用同一套 Unicode NFKC 规范化。去除查询首尾空白，将连续 Unicode 空白视为词项分隔，不把用户输入作为正则表达式或隐式通配符执行。
- 拉丁字母及其他有 Unicode case-fold 规则的字符不区分大小写；中文、数字及无大小写字符按规范化后的原字符匹配。后端检索、`total_count`、match offsets 和前端高亮必须共享同一规范化/映射规则。
- 查询中由空白分开的多个非空词项使用 AND 语义：所有词项必须出现在同一条消息的可搜索语料中，出现顺序不限、无需相邻。连续输入且没有分隔的文字仍作为一个完整词项处理。
- 第一阶段不提供 OR、NOT、引号语法、正则、模糊匹配、拼音、词干、同义词、错别字纠正或语义扩展。语义召回属于 AI/语义搜索，不混入可验证的普通关键词结果总数。
- sidecar 返回每个命中词项在安全 `matchSnippet` 中的规范化映射位置；前端不得再次用自己的大小写或字符串规则搜索正文。若原文与规范化文本长度发生变化，后端必须返回可渲染的片段分段或原文 offset map，避免高亮错位。
- 例：`Project  发票` 规范化为两个词项，可命中同一条消息中任意顺序出现的 `project` 与 `发票`；只出现其中一个词项的消息不算命中。
- 测试覆盖全角/半角、大小写、多个空格、制表符、换行、组合字符、特殊正则符号、纯空白、重复词项和规范化后为空等边界，并证明后端命中数量与页面高亮一致。

#### 已确认：移除没有分数契约的“相关性排序”

- 当前 sidecar 不返回相关度分数，普通关键词搜索基线又按时间倒序输出；现有 `relevance` 模式只是原样保留消息数组，实际效果与“时间从新到旧”重复，不能称为相关性。
- 正式搜索页、状态类型、筛选摘要、导出元数据和测试中移除 `relevance` 及“相关性（需要后端支持）”禁用项。用户界面不展示开发占位或无效能力。
- 排序只保留“时间从新到旧”（默认）和“时间从早到晚”，二者继续即时整理当前已加载结果，不纳入统一筛选草稿或“应用筛选”。
- 后端基线顺序、当前时间倒序和 source index 的关系必须在状态模型中明确；同一时间戳使用不可变 `sourceIndex` 作为稳定 tie-breaker，避免本地正序/倒序产生随机行序。
- 未来只有在 sidecar 返回可解释的逐条 score、定义稳定的同分排序、支持跨页全量一致排序并完成命中原因展示后，才能重新立项相关性排序；不能仅凭数组原顺序恢复该名称。

#### 已确认：最近搜索默认开启，但有明确期限和隐私边界

- “记住最近搜索”作为本机便利偏好默认开启。只在用户显式提交且后端成功建立 applied result snapshot 后记录规范化关键词；输入过程、空查询、校验失败、取消、网络/数据库失败和仅修改筛选都不写入历史。
- 最多保留最近 5 条，每条保存创建/最后使用时间并在 30 天后自动过期。相同规范化关键词移动到首位并刷新时间，不增加重复项；读取时清除损坏、超期或不符合当前长度规则的数据。
- 历史只保存规范化关键词与必要时间戳，不保存范围、会话 ID、类型、日期、结果数量、打开位置或消息内容；不进入诊断、日志、导出、同步或远程请求。
- 隐私模式的既定职责是遮罩屏幕内容而不破坏工作状态。开启时历史不渲染到 DOM/可访问树，并暂停新增记录；关闭后恢复仍在期限内的历史，不再像当前实现一样自动删除本机记录。
- 搜索建议浮层支持单条删除和“清空最近搜索”。设置中的“记住最近搜索”开关关闭时停止记录并删除现有历史；开关说明在用户操作前明确该结果，不再增加二次确认对话框。
- 历史默认不占据搜索框下方的永久布局。只有输入框获得焦点、查询草稿为空且隐私模式关闭时，才在轻量建议浮层中显示；选择一项只填入并按正常显式搜索路径执行，不绕过当前筛选草稿与校验。
- 存储结构需要版本与迁移。现有无时间戳的字符串数组升级时按一次性迁移策略处理，不能赋予无限期限；测试覆盖默认开关、30 天边界、时钟异常、重复项、单删/全删、关闭开关、隐私模式往返和 localStorage 失败。

#### 已确认：关键词上限为 200 个可见字符和 20 个词项

- 在 NFKC 规范化、首尾 trim、连续空白折叠和重复词项去重后，查询最多包含 200 个 Unicode grapheme cluster（用户可见字符）与 20 个 AND 词项。空查询或规范化后为空仍按不提交处理。
- 不能直接依赖 HTML `maxLength` 或 JavaScript UTF-16 `length`，否则表情、组合字符和部分 Unicode 字符会被错误计数。前端优先使用 `Intl.Segmenter` 的 grapheme 语义并提供经过同一测试语料验证的 fallback；sidecar 使用等价规则或接收前端规范化查询后再次安全校验。
- 用户输入或粘贴超限时保留完整草稿，不静默截断、不自动删除词项。搜索按钮与 Enter 提交禁用，并在输入附近就地说明 `关键词最多 200 个字符` 或 `一次最多搜索 20 个词`；不发送请求、不改 applied request、不写入最近搜索。
- 字符计数默认不常驻，只在达到 160 个可见字符后显示；超限时显示当前值/上限。错误与计数不得改变搜索框高度或把统一条件栏挤成额外一行。
- IME composition 期间不执行最终长度错误、不提交搜索；`compositionend` 后重新规范化和校验。粘贴、撤销、选择最近搜索和程序化恢复草稿走同一验证路径。
- sidecar 对绕过前端的超限或超词项请求返回明确的参数错误，不执行代价高昂的扫描。前端按参数错误展示字段级恢复，不翻译为“网络连接失败”。
- 测试覆盖 199/200/201 grapheme、20/21 词项、重复词、全角空格、组合 emoji、超长粘贴、IME 上屏、撤销到合法值、历史迁移中的超限项和直接 API 调用。

#### 已确认：保留旧结果、显式刷新、绝不混合数据快照

- 首次成功搜索建立不可混合的 result snapshot。sidecar 返回 `snapshotId` / `dataRevision` 与稳定 continuation；后续分页、向前/向后累积、无限加载、缺口补载和全部命中导出必须携带同一快照身份。
- 若本地数据库更新导致快照失效，已加载结果、active result、缓存区间、分组/排序和滚动位置继续保留为可读的 stale snapshot；停止向其中追加新数据，也不能把新 revision 的页面合并进去。
- 结果工具条以紧凑文字显示 `数据已更新` 和无边框“刷新搜索”，不使用警告卡片或彩色横幅。加载更多、缺口补载和全部命中导出在 stale 状态下禁用并说明需要先刷新。
- 不自动重跑搜索。用户点击“刷新搜索”时重新执行当前 `SearchAppliedRequest`，清理旧 page/range/gap cache 并建立新快照；尚未应用的关键词或筛选草稿原样保留，不被刷新动作偷偷提交。
- 刷新后优先用稳定消息 ID 恢复 active result，并按新的 `sourceIndex` 定位；消息已不存在时选择新结果首条并礼貌公告，不把另一条消息伪装成原 active result。
- 已启动的全部命中导出必须绑定快照。快照失效时取消任务、删除/放弃临时文件并给出“数据已更新，请刷新后重试”，不能生成跨 revision 的混合文件；当前已加载导出仍可明确导出冻结的 stale 部分快照并标记其 revision 状态。
- 若 sidecar 无法跨请求维持数据库快照，至少提供可验证 revision 和确定性 keyset/cutoff；检测到 revision 变化即返回专用冲突错误。前端不得把冲突翻译为普通网络失败或自动从 offset 继续。
- 测试覆盖新消息追加、旧消息删除/更新、会话新增、三种浏览方式、双向/缺口加载、脏筛选草稿、刷新定位、部分导出和全量导出中途失效。

#### 已确认：关键词进入统一草稿，提交动作按状态改名

- `SearchDraft` 包含关键词、范围、消息类型和日期；`SearchAppliedRequest` 是最近一次成功提交并与结果快照绑定的规范化版本。排序、分组和浏览方式仍是本地 view preference，不进入该草稿。
- 输入、粘贴、选择最近搜索或点击清除图标只更新关键词草稿，不自动请求、不取消进行中的已应用结果请求，也不清空稳定结果。移除当前 300ms 输入即搜路径。
- 页面只保留一个稳定 commit action slot：首次执行、关键词变化、或关键词与筛选同时变化时显示“搜索”；只有范围/类型/日期变化且关键词等于 applied keyword 时显示“应用筛选”。两个动作不得同时出现。
- 无论动作显示“搜索”还是“应用筛选”，提交都使用当前完整且合法的 `SearchDraft` 建立一个新的 applied request 与 result snapshot，避免某个按钮只提交一半状态。
- “取消修改”一次恢复关键词、范围、类型和日期到最近 applied request。没有已应用请求时，取消恢复该入口的初始默认值；动作需要可撤销但不增加确认对话框。
- 关键词草稿为空、超限、词项过多或日期非法时，唯一提交动作禁用并就地说明具体字段问题；旧结果继续显示，结果标题和可访问说明始终引用 applied keyword，不能被未提交输入改写。
- Enter 与当前 commit action 完全等价；IME composition 期间不提交。动作所在布局槽位具有稳定宽度，状态改名不造成条件栏或结果区域位移。
- 关键词输入的清除图标只清空草稿。它不再调用当前会同时清除 query/results 的 `onClearSearch()`，也不承担结束当前搜索的隐藏副作用。

#### 已确认：通过显式命令结束搜索，Escape 永不清除稳定结果

- 不增加常驻“清除结果”按钮。结果工具条的单个轻量更多菜单提供“结束当前搜索”，与浏览方式、导出等命令保持清楚分组；菜单触发器使用无边框图标和可访问名称。
- “结束当前搜索”取消页面搜索、分页、双向/无限加载和缺口补载，清除 applied request、result snapshot、loaded ranges/gaps、active result、页面错误和滚动恢复快照，并把焦点移回关键词输入。
- 该命令清空关键词草稿，但保留当前范围、类型和日期作为下一次搜索草稿；浏览方式持久化偏好、最近搜索记录及“记住最近搜索”设置不受影响。
- 操作不删除聊天数据、导出文件或最近搜索，因此无需确认对话框。若独立导出任务正在写文件，应按导出任务自己的取消/完成规则处理，不能由页面清理静默留下损坏文件。
- 输入框清除图标只清空关键词草稿；“清除筛选”只修改范围/类型/日期草稿；“清空最近搜索”只删除本机历史；“结束当前搜索”只结束当前 applied task。文案、handler 和测试不得交叉复用。
- Escape 的优先级固定为：关闭最上层对话框/菜单/日历/建议浮层；没有浮层且存在未应用修改时执行一次“取消修改”；没有浮层且草稿干净时不改变 applied request 或结果，可仅移除输入焦点。
- Escape 永不直接结束搜索、删除历史或清除稳定结果。键盘公告只描述实际发生的关闭/取消，不播报敏感关键词。
- 测试覆盖各浮层层级、脏关键词、脏筛选、空关键词、加载中、stale snapshot、结束后焦点、重新搜索时保留筛选以及四种清除命令互不串线。

#### 已确认：按稳定来源直接定位，失败只影响当前结果行

- 搜索结果契约为每条消息返回稳定 `chatId`、`messageId` / `localId`、时间戳和 snapshot revision；可读会话名只用于展示，不能代替来源标识或作为唯一导航键。
- 点击结果后，L2 直接按稳定 chat ID 解析/补取会话元数据并请求目标消息上下文，不以 `chat.conversations` 当前是否已经加载该项作为前置条件。只有定位成功后才导航到会话工作台。
- exact message 定位失败时保留搜索页面、其他结果和当前阅读位置，仅在对应结果行显示恢复状态。不得调用全局 `setError()` 把整页结果替换成错误态。
- 行内首先提供无边框“重试定位”。若会话仍存在且有可信时间戳，再提供“打开该时间附近”；该降级必须由用户明确选择，不能自动把邻近消息冒充为原命中。
- 使用时间附近定位后，会话页固定显示 `原消息未找到，当前显示其时间附近的记录`，并保留返回搜索入口。会话本身也不存在时不提供伪定位，只提供“刷新搜索”。
- 返回搜索页恢复完整 applied/result snapshot、active result、滚动锚点、loaded ranges/gaps、浏览方式、排序/分组及未应用草稿。当前 `ChatReturnToSearch` 仅保存窄查询快照，需升级为版本化恢复状态或可重建引用。
- 结果行错误包含 `missing-chat-id`、`conversation-unresolved`、`message-not-found`、`context-load-failed` 和 `snapshot-stale` 等非敏感原因；诊断不得写入 chat ID、消息 ID、关键词或正文。
- 测试覆盖会话列表未加载、超过列表首批范围、会话元数据补取、精确消息删除、时间附近显式降级、全局其他结果保持可用、返回恢复和一次 Enter 只触发一次导航。

#### 已确认：范围是“全部 / 当前 / 指定会话”的互斥联合

- 搜索范围正式建模为 `all | current(chatId) | selected(chatIds)` 三种互斥状态。`current` 必须恰有一个稳定 chat ID，`selected` 必须至少包含一个去重后的稳定 chat ID；不存在“current 再附加 selected chats”的并集状态。
- 全部会话是全局导航入口的默认；当前会话是具有有效上下文入口的默认/强化状态；指定会话允许选择一个或多个会话。入口默认只影响初始草稿，不改变三种状态的统一提交规则。
- 三种选择都位于同一个无边框范围触发器和菜单。选择“指定会话”后进入可搜索会话选择器，不创建独立高级筛选卡片、永久 chip 行或第二个范围入口。
- 指定会话选择器查询后端完整会话目录并按稳定 ID 选择，不依赖前端当前会话列表首批数据。搜索、分页、无结果、目录失败和重试都有独立状态。
- selected 为空时草稿非法且不能提交；选择完成后主页面只显示紧凑摘要，如 `指定会话 · 3`。具体会话名称留在选择器/摘要浮层中，不在条件栏横向铺开。
- 指定会话变化属于统一 `SearchDraft`；点击“搜索 / 应用筛选”后才建立新 applied request。取消修改恢复完整范围种类与 chat ID 集合。
- 隐私模式下保留范围种类、选择数量、选中状态和可操作结构，但会话名与搜索建议均使用隐私安全文案；chat ID 不出现在 DOM 可访问名称、日志或诊断中。
- L2 将判别联合映射为后端 chats 参数或稳定 scope token，且覆盖 all/current/selected 的完整性、重复 ID、陈旧 ID、超长选择集合和请求长度测试。

#### 已确认：本轮补齐真实发送者筛选，但不占据主条件栏

- 发送者不进入普通关键词语料，本轮通过向后兼容方式为 `/api/v1/search` 增加真实后端发送者筛选。该能力必须与完整性、真实总数、稳定快照和三种浏览方式一起验证，不能只做前端已加载结果过滤。
- 发送者选择支持一个或多个稳定 sender ID；同一发送者维度内使用 OR，与关键词、范围、消息类型和日期使用 AND。显示名仅用于辨识，不能作为请求唯一键。
- 选择器根据当前范围查询完整可用发送者目录：当前/指定会话优先显示相关参与者，全部会话支持全局目录搜索。重名项显示最少必要的会话/账号辨识信息；当前用户使用“我”而不是内部账号 ID。
- 主条件栏继续只常驻范围、类型和日期。发送者位于一个无边框“更多筛选”触发器的轻量浮层中，默认收起；未启用时不新增页面行、卡片或永久说明。
- 启用后主栏仅显示紧凑 `发送者 · n` 摘要或同一触发器的文本状态，不为每位发送者生成 chip。发送者变化进入统一 `SearchDraft`，仍由唯一“搜索 / 应用筛选”动作提交。
- 收藏、附件和其他没有真实端到端能力的项目不出现在浮层。文件/媒体使用消息类型维度；未来新增筛选必须先有 sidecar 契约、完整性测试和可解释结果。
- sender capability 尚未实现或验证失败时，整个入口隐藏且 applied state 不允许构造 sender 条件；不能显示“需要后端支持”的禁用开发占位。版本降级时保留可恢复提示但不发送无效参数。
- 隐私模式隐藏发送者名称及搜索输入，但保留已选数量、清除和取消/应用结构。测试覆盖重名、自己/他人、群聊、跨会话、多选 OR、范围变化导致选择失效、目录失败和隐私可访问文本。

#### 已确认：消息类型采用共享产品分类和紧凑多选

- 类型维度从单个 raw `msg_type` 改为用户可理解的多选产品分类：`文本`、`图片与表情`、`视频`、`语音`、`文件`、`链接与卡片`、`引用与转发`、`位置`、`系统与其他`。
- 同一类型维度内使用 OR；与关键词、范围、发送者和日期使用 AND。默认“全部类型”等价于不限制类型；选择“全部类型”清除其他类型选择，不把它与具体类型并存。
- 主条件栏仍只有一个类型触发器。单选显示分类名，多选显示 `类型 · n`，不生成第二行 chip；菜单使用紧凑复选项并提供清除选择，键盘支持方向键、Space、Enter 和 Escape。
- sidecar 维护产品分类到 type/subtype 的权威映射并接受稳定 category keys，而不是要求前端拼装脆弱的数字组合。前端 capability contract 获取同一分类目录，结果与导出返回统一 `messageCategory`。
- `文件` 只匹配 `MessageTypeShare=49` 且 `MessageSubTypeFile=6`；链接、小程序、视频号、音乐和名片归入“链接与卡片”；引用、合并转发与笔记归入“引用与转发”。图片/动画表情、系统事件及其余 subtype 也必须有明确、不重叠的映射表。
- 未知新 type/subtype 默认进入“系统与其他”，并始终包含在“全部类型”中；诊断可以记录非敏感数值计数，但普通 UI 不显示原始代码。
- 类型选择进入统一草稿，并由唯一提交动作应用。结果行标签、空态建议、筛选摘要、后端计数和导出类型都使用同一个 `messageCategory`，不能各自重新推断。
- 合成测试为每个已知 type/subtype 至少构造一条消息，验证单类、多类 OR、与其他维度 AND、全部类型、未知类型和“文件不含链接/引用”回归。

#### 已确认：结果使用整行可打开、正文可选择的无卡片结构

- 默认结果列表使用连续、无卡片外框的语义结果行，行间仅有必要分隔线。不得为每条消息重复绘制边框、阴影、圆角容器和文字“查看”按钮。
- 每行固定信息层级为：会话名称；发送者、`messageCategory` 与时间；最多两行安全 `matchSnippet`。即使范围是当前会话也保留会话来源，全部/指定会话下不得省略。
- 非正文命中显示短来源标签，如“文件名”“链接标题”或“引用内容”；标签使用普通次级文字，不做彩色 badge。关键词高亮只依据后端返回的 match segments。
- 设置稳定的小型媒体槽。图片/视频有安全缩略图且隐私模式关闭时显示真实缩略图；其余类型显示统一图标，占位尺寸不随内容变化。加载、失败和无预览状态不能造成行高或文本横跳。
- 结果主体是一个语义链接/可导航命令，单击或 Enter 打开精确上下文；行尾仅放 aria-hidden 的轻量箭头提示，不再嵌套第二个“查看”按钮。移除当前原生 button 同时监听 Enter 的双触发路径。
- 用户拖选命中片段或元数据文字时不触发导航，可使用系统复制。实现不得通过全行 `user-select: none` 获得点击感；触摸设备的轻微移动也不能误打开。
- 上/下方向键只移动 active result 并保持焦点可见，Enter 执行一次打开。active 状态使用低对比中性背景和细左侧强调线，保持文本对比，不把每行变成彩色选中卡片。
- 隐私模式保持行高、媒体槽、元数据位置、分组和键盘结构完全一致，只替换敏感文字/缩略图并使用隐私安全可访问名称，避免遮罩导致布局坍缩。
- 响应式验收覆盖长会话名、长发送者名、200 字关键词、高亮跨行、文件名、缺少时间、缩略图失败、200% 缩放、320/390px、键盘与触摸文本选择。

#### 已确认：三种非折叠分组，排序/分组模式跨重启记忆

- 分组只保留 `不分组`（默认）、`按会话分组`、`按日期分组`。日期组使用 applied request 冻结的本机自然日语义；不增加按发送者、类型等低频组合，避免结果工具条膨胀。
- 排序仍只有“时间从新到旧”（默认）和“时间从早到晚”。排序与分组只转换当前 retained loaded results，不请求后端、不修改 source index、不进入统一筛选草稿。
- 分组标题显示 `已加载 n 条`，不显示或暗示全量组计数。会话组按当前排序后第一条成员的视觉位置排列，组内保持同一时间顺序；日期组顺序随时间排序方向变化。
- 第一阶段分组不提供折叠。所有已加载结果保持可见，避免 active result 被隐藏、方向键跨组失效、视觉数量与“已加载”不一致以及额外的折叠持久化状态。
- 最后选择的 sort/group mode 作为非敏感本机展示偏好跨关键词搜索、筛选应用、离开/返回页面和应用重启保留。只保存白名单枚举，不保存会话名、日期组键、结果 ID、滚动位置或任何私密内容。
- 排序/分组菜单提供“恢复默认整理”，即时回到时间从新到旧和不分组，不改变 applied request、缓存区间或 active result。损坏/旧版偏好同样回退到该默认。
- 隐私模式不清除模式偏好，但会话组标签和可访问文本继续脱敏。新搜索使用记住的模式整理首批 50 条，并明确显示“仅整理已加载结果”。
- 测试覆盖跨搜索/重启恢复、损坏值、日期自然日、会话重名、相同时间戳 tie-break、恢复默认、非连续范围 coverage row 和隐私模式。

#### 已确认：零结果建议只修改草稿，绝不自动扩大范围

- 成功返回 0 条是独立的 no-results snapshot，必须与首次未搜索、服务/数据库未就绪、请求失败、能力受限和当前加载区间为空区分，不能共用“没有结果”文案。
- 零结果区域靠近结果起点使用紧凑无卡片布局，复述隐私安全的 applied keyword、范围和有效限制；不再用大块居中空态把主要控件与恢复操作拉开。
- L2 根据实际 applied restrictions 最多生成 2–3 个针对性恢复建议，例如清除日期、改为全部类型、清除发送者或改为全部会话。没有对应限制时不显示无效建议。
- 点击恢复建议只修改统一 `SearchDraft`，不立即请求、不改写 no-results applied snapshot。唯一 commit action 随状态显示“应用筛选”，由用户检查后显式提交。
- 不提供含义不明确的全局“清除筛选”快捷动作，也不自动删除关键词词项、切换范围或放宽日期。范围扩大尤其必须由用户看见并确认，保持本地私密搜索的最小授权原则。
- 只有关键词且无其他限制时，提供“修改关键词”将焦点移回输入框并选择适当文本；不替用户猜测拼写、删除 AND 词项或执行语义搜索。
- 建议动作使用无边框文字命令，数量有限且不形成按钮墙。草稿变化后的状态说明与提交动作保持在主条件区，不在空态复制第二套 Apply 控件。
- 测试覆盖每种单/组合限制、无可放宽条件、隐私文案、草稿取消、键盘焦点、建议后提交失败以及零结果与各类错误状态的互斥性。

#### 已确认：新请求成功后才替换 last-known-good 结果

- `SearchAppliedRequest` 与稳定 result snapshot 只在 replacement search 成功后原子更新。用户提交的合法草稿先形成独立 `PendingSearchRequest`，不能在请求开始时提前覆盖 applied truth。
- 已有结果时，pending 期间继续显示并允许读取/打开 last-known-good 结果、active result、缓存区间和滚动位置。结果标题仍引用旧 applied 条件，并以轻量 `正在准备新结果` 明确存在 pending 请求。
- 不清空列表、不铺整页遮罩、不把旧结果标记为新条件，也不使用会阻止阅读的中央 spinner。唯一 commit slot 显示进行中状态并提供明确取消，列表本身不伪装成 `aria-busy` 的新结果。
- pending 成功后一次性替换 applied request、snapshot、ranges/gaps、active result 和结果视图；普通新搜索回到首条，新 revision 刷新则按已确认规则尝试恢复稳定 active ID。
- pending 失败时保留旧 applied/results，草稿继续保持未应用，提交区域显示服务/数据库/参数/超时等准确错误和“重试”。不得调用全局结果错误把 last-known-good 列表隐藏。
- 用户取消 pending 时只终止该请求并清除 pending 状态，旧结果与草稿均保留。再次提交会取消旧 pending 并建立新 request ID；任何迟到响应都必须被 snapshot/request identity 拒绝。
- 第一次搜索没有 last-known-good 时，结果区域显示稳定尺寸骨架；失败后在同一区域显示完整错误恢复。取消首次请求回到未搜索状态，保留草稿，不生成虚假空结果。
- 等待期间打开旧结果继续携带旧 snapshot/return state；不能把 pending 草稿写入会话导航或返回搜索摘要。
- 测试覆盖首次/替换搜索、快速连续提交、取消、超时、参数错误、失败后重试、旧结果打开、迟到响应和成功原子切换时无布局跳动。

#### 已确认：自动检测就绪，但搜索与重试只由用户显式触发

- 搜索页消费真实 service/http/database readiness，不再调用硬编码 `true` 的 ready model。系统健康检查可以自动轮询状态，但不能排队或自动提交用户的关键词/筛选草稿。
- 服务启动或数据库加载期间允许编辑完整草稿，唯一 commit action 禁用并就地显示 `正在启动本机搜索服务` 或 `正在加载聊天数据库`。状态变为 ready 后只启用动作，不自动执行之前的输入。
- 服务启动失败提供“重新启动本机服务”；数据库未配置/不可用提供“前往设置”或“重新加载数据库”。动作复用 L2 的真实恢复编排，不让搜索分子直接调用网络/系统原子。
- 正常搜索超时、运行中服务中断和未知响应不自动重试，避免重复执行昂贵全库扫描。last-known-good 结果与草稿继续保留，由用户通过同一提交/重试路径显式执行。
- 错误翻译至少区分：服务启动中/失败、HTTP 未就绪、数据库未就绪、参数字段错误、请求超时、用户取消、snapshot/revision 冲突、权限/文件问题和未知响应。不得全部显示“检查网络连接”。
- 参数错误回到对应关键词、范围、类型、发送者或日期控件；snapshot 冲突走“刷新搜索”；取消不显示错误。只有未知错误才提供隐私安全诊断入口。
- readiness 与错误提示使用主条件区/结果工具条的紧凑状态行，不增加独立警告卡片、彩色 banner 或重复的页面级状态面板。live region 只公告状态转折，不反复播报轮询。
- 测试覆盖冷启动、慢启动、启动失败、数据库未配置/加载中、ready 后不自动搜索、运行时掉线、超时、取消、恢复动作和隐私安全诊断。

#### 已确认：日期辅助路径只保留四个高频快捷范围

- 日期 popover 只提供 `今天`、`最近 7 天`、`最近 30 天`、`本月` 四个快捷范围；最近 n 天包含点击当天，本月为本月 1 日至当天。所有计算使用点击时的本机自然日。
- “清除日期”是 popover 中的无边框命令，不做成第五个范围按钮。第一阶段不增加昨天、本周、本季度等低频项；任意自定义范围使用已确认的整体数字输入和日历。
- 单击一个日历日期立即形成该日的一天范围，用户可以直接关闭；继续选择另一日期扩展为范围，反向选择时自动规范化为较早日期至较晚日期。
- 快捷范围、日历日期和清除日期都只更新统一草稿，不发起请求、不关闭 last-known-good 结果。最终提交时重新验证并冻结本机时区边界。
- 日历前后月份导航必须真实改变月份、日期网格和焦点，不再保留静态原型按钮。跨年、不同月天数、闰年和当前选区跨月都有确定状态。
- 键盘支持方向键按日移动、PageUp/PageDown 切月、Enter/Space 选择、Escape 关闭并把焦点返回日历触发器；范围状态通过可访问名称/live region 简短公告。
- 快捷项使用普通无边框菜单命令或短文本选项，不绘制成成排有框按钮；选区只使用克制的现有强调色和范围背景，不引入新色系。
- 测试冻结系统时间并覆盖今天、7/30 天、本月首日、跨月/跨年、夏令时、反向范围、月份导航、键盘和 320/390px popover 定位。

#### 已确认：选择最近搜索只填入草稿，仍需显式提交

- 最近搜索建议是关键词草稿来源，不是隐藏的第二个提交入口。单击或用键盘 Enter 选择历史项只写入 keyword draft，不执行搜索、不应用范围/类型/日期/发送者草稿。
- 选择后关闭建议浮层，把焦点返回关键词输入，唯一 commit action 显示“搜索”。用户可以继续编辑历史词、检查筛选，再通过同一显式路径提交。
- 已有 last-known-good 结果、active result 和滚动位置在选择历史词后保持不变；结果标题继续引用 applied keyword，不能提前改成历史词。
- 建议列表中的单条删除只删除该历史记录，不填入、不提交，也不改变当前草稿。清空历史遵守已确认的本机记录策略。
- 键盘语义为：方向键移动建议，第一次 Enter 选中并填入，浮层关闭；第二次 Enter 才执行当前完整合法草稿。IME composition 仍优先于建议与提交。
- 该规则消除当前 `onUseRecentQuery`、`onSearch`、`onExecuteSearch` 连续调用可能造成的重复/自动提交，并与单一 commit action 状态机保持一致。
- 测试覆盖点击、键盘两次 Enter、删除图标、脏筛选、旧结果保留、隐私模式、历史过期和一次选择不会产生后端请求。

### 功能范围

- 关键词：输入、清除、最近搜索、Enter/搜索按钮提交、空查询阻止、隐私模式隐藏历史。
- 筛选：范围、消息类型、日期统一草稿；应用、取消修改、清除单项、首次搜索合并提交。
- 请求：后端 `/api/v1/search`、20 条分页、取消、超时、stale response 防覆盖、加载更多合并校验。
- 结果：总数/已加载数、会话归属、发送者、时间、命中片段、键盘导航、跳回上下文。
- 整理：排序与分组只作用于已加载结果，独立于后端筛选草稿。
- 导出：面板同时提供全部命中和当前已加载，默认全部命中；全量路径必须新增独立任务、进度、取消、快照校验和大文件策略。
- 状态：未开始、草稿变更、搜索中、成功、空结果、筛选后空结果、取消、超时、服务不可达、数据库未就绪、加载更多失败。

### 极简 UI 语法

- 边框只用于输入边界、popover 外轮廓、必要分隔线和错误状态；普通按钮、菜单触发器、快捷日期、导出、翻页、结果跳转默认无边框。
- 只有“搜索”使用稳定实心蓝色。`应用筛选`用无边框蓝色文字表达上下文动作，避免同一区域出现两个实心主按钮。
- hover 用 `--surface-hover`，selected 用 `--surface-selected`，focus 保留清晰焦点环；去掉边框不等于缩小点击区域或取消可访问状态。
- 页面不新增绿色/橙色状态 chip；命中高亮、成功/错误等语义色只在需要传达信息时出现。
- 按钮文字只保留明确命令。常用图标动作使用 Lucide 图标、可访问名称和 tooltip，不再用带边框小胶囊承载每个动作。

### 筛选状态模型

| 状态 | 界面表现 | 请求行为 |
| --- | --- | --- |
| 首次进入 | 草稿和已应用条件均为入口默认值 | 不发送空查询 |
| 首次搜索前修改筛选 | 只更新草稿，不额外显示“未应用”警告 | 点击搜索时关键词与草稿一次提交 |
| 已有结果且草稿未变 | 不显示应用操作 | 结果对应已应用条件 |
| 已有结果且草稿变更 | 显示“筛选尚未应用”、取消、应用筛选 | 不自动请求，旧结果保持稳定 |
| 点击应用筛选 | 禁用重复提交并显示搜索中 | 草稿复制为已应用条件，取消旧请求，生成新快照 |
| 点击取消 | 草稿恢复为已应用条件 | 不发送请求 |
| 日期半输入或非法 | 日期字段显示错误，应用不可用 | 不改变已应用条件，不发送请求 |
| 排序/分组变化 | 结果工具条立即更新 | 只整理当前已加载结果 |

### 1. 这个页面到底帮助用户完成什么任务？

应该是：用户用关键词在聊天记录中查找证据，按会话、时间、消息类型、发送者、附件/收藏等条件缩小范围，并从结果跳回原始聊天上下文。

当前页面的问题是：它看起来像一个筛选调试面板，而不是一个完成搜索任务的页面。用户第一眼看到的是范围卡片、搜索框、高级筛选、空结果，而不是“我现在会搜索哪些数据、输入什么、结果来自哪里”。

### 2. 用户第一步应该做什么？

第一步应是确认搜索范围并输入关键词。范围不应该占用三行，也不应该同时以 chip、按钮和抽屉触发器三种形式出现。默认场景下，范围、类型和日期应位于一条紧凑条件栏；当前没有真实能力的高级条件直接移除，未来新增能力时再使用轻量 popover/sheet。

### 3. 同一任务是否有过多入口？

是。范围和消息类型同时存在于：

- 已生效 chips；
- 内联按钮组；
- 右上角范围设置图标打开的菜单；
- 结果区的高级筛选 chips。

这些入口不是完全等价的：范围 chip 默认只在当前会话时可清除，消息类型 chip 只在非全部类型时出现，高级筛选 chips 不包含范围和消息类型。用户因此无法形成统一规律。

### 4. 用户犯错后能否立即恢复？

部分能，但不够明确。页面有“重置范围”“清除筛选”“清除搜索内容”，但它们清理的对象不同。日期输入错误会被静默忽略或被错误归一化的风险更高：当前 `parseDateParts()` 只匹配 `YYYY-MM-DD`，没有校验 13 月、32 日、闰年等真实日期合法性。错误输入不应进入搜索，也不应静默变成另一个日期范围。

### 5. 是否有缺失能力在拖累当前体验？

有。发送者、收藏、附件筛选已经以状态字段存在，但后端不支持，当前 UI 只是用三个小标签告知“需要后端支持”。这对用户没有操作价值，反而增加噪音。排序和分组只作用于已加载结果，也会让用户误以为搜索结果全量重排。

## Grilling 逐项质询

这一节按页面区域逐项拷问。判定标准只有一个：如果用户无法预测控件作用、无法理解状态来源、无法恢复错误，控件就不合格；不是“能点”就算完成。

### 搜索范围卡片

**质询：这个卡片为什么要占这么大的首屏空间？**

不成立。当前范围卡片把同一个问题拆成标题说明、范围 chip、范围按钮、类型按钮、重置按钮、设置图标。用户要完成的是“我要搜哪里”，不是阅读一个范围系统的说明书。三行布局在信息量上没有增加确定性，只增加了认知成本。

**质询：为什么范围有永久 chip，类型没有永久 chip？**

不成立。范围和类型都是筛选维度，规则却不同：范围默认也显示 chip，类型只有非默认时才显示 chip。用户会自然追问：如果“范围：全部会话”需要常驻，那为什么“类型：全部类型”不常驻？如果默认类型不需要常驻，默认范围也不该常驻。

**质询：点击当前会话和全部会话的结果是否可预测？**

不够。代码有切换逻辑，但当前会话是否可用依赖 route、selected conversation、conversation list load 状态。UI 不应让用户在一个看起来可点的按钮上猜原因。当前会话不可用时，应显示明确下一步：“从会话工作台选择会话”或“保持全部会话”，而不是只用弱提示解释。

**必须改变：**

- 范围、类型和日期共用一个 `SearchConditionBar`，而不是一个大卡片。
- 默认值和非默认值都直接替换同一个触发器文本，不再生成第二行 chip。
- 范围菜单同时承载全部会话、当前会话和指定会话入口，不再保留重复的设置图标。
- 范围、类型和日期全部写入同一份筛选草稿；取消与应用对整份草稿生效。

### 搜索内容

**质询：用户输入后到底搜哪里？**

当前页面没有直接回答。代码会请求 `/api/v1/search`，但用户无法从 UI 判断这是后端全库检索、后端当前分页检索、语义索引检索，还是前端已加载数据过滤。搜索产品不能让用户猜数据边界。

**质询：空查询为什么只说“不提交空白查询”？**

这句话技术上正确，但不是用户任务语言。用户更关心：“我现在会搜全部会话还是当前会话？能搜图片/文件吗？没有结果时下一步是什么？”空态应根据当前范围和筛选生成任务级建议，而不是只解释请求行为。

**必须改变：**

- 搜索框下方或结果工具条显示“后端检索：全部会话 / 当前会话 / 指定会话；已加载 x / 共 y”。
- 空态显示当前范围、类型、日期摘要。
- 结果为 0 时给出具体恢复动作，例如清除日期、切回全部类型、切回全部会话。

### 高级筛选

**质询：为什么“高级筛选”默认铺在主页面？**

不成立。高级筛选不是主任务第一步。默认展开导致结果区被挤到更低位置，尤其在 768 高度桌面上，用户先看到的是筛选表单而不是搜索结果。进一步检查后确认，当前所谓高级筛选中只有日期是真正的后端条件，而日期已经进入主条件栏；剩余内容不是本地结果整理，就是后端未支持能力。因此现阶段应删除整个空壳区域，而不只是折叠它。

**质询：为什么日期需要用户自己输入横杠？**

不成立。既然界面已经知道格式是年四位、月两位、日两位，就应该让输入结构直接表达格式。要求用户手动输入 `-` 是把格式维护成本转嫁给用户，尤其在重复筛选时很低效。

**质询：当前日期输入是否会阻止错误搜索？**

不够。当前 `DateInput` 只设置 `pattern`，L2 只匹配字符串格式。真实日期合法性、闰年、月日范围、起止顺序都需要显式校验。不能把非法日期静默当成“无筛选”或交给 `Date.UTC` 自动归一。

**质询：为什么把“发送者/收藏/附件需要后端支持”永久展示出来？**

不成立。不可用能力不是用户的主任务内容。永久展示三个不可用标签会制造“这里本来应该可以筛选但不能用”的挫败感。它们应该留在能力规划和开发诊断中，不进入普通用户界面；只有后端实现后才设计真实控件。

**必须改变：**

- 移除当前高级筛选区域和“更多筛选”空入口；日期、指定会话分别归入日期控件和范围菜单。
- 日期改为单值驱动的整体日期范围控件。
- 非法日期阻止应用，并给字段级错误。
- unsupported 筛选不进入普通用户界面。

### 排序与分组

**质询：用户会不会以为排序/分组作用于全部搜索结果？**

会。当前文案说“排序和分组只整理已加载结果”，但它被放在高级筛选区域里，和日期这些后端筛选并列。用户很可能认为点击“时间从早到晚”会重新排序所有命中，而不是当前加载的 20 条。

**必须改变：**

- 短期把排序/分组移到结果工具条，标注“已加载结果”。
- 中期如果要放回筛选区，必须接入后端排序/聚合能力。
- 导出时必须说明导出排序后的已加载结果，还是全部命中结果。

### 结果区与空态

**质询：搜索结果能不能让用户立刻判断命中来自哪里？**

不够。默认 flat 模式下结果行没有稳定展示会话名，全部会话搜索时用户只能看到发送者和时间。搜索结果的最低信息单元应是“会话 + 发送者 + 时间 + 命中片段”。

**质询：结果区是不是承担了“搜索真实性”的解释？**

还不够。它显示已加载数和总数，但没有说明总数来自后端，不说明排序/分组的作用范围，也没有说明“加载更多”继续使用同一查询条件。

**必须改变：**

- flat 结果行显示会话归属。
- 工具条显示搜索范围、后端检索、已加载/总数、当前本地整理方式。
- 加载更多按钮文案改成“加载下一页后端结果”或等价文案。
- 跳回上下文失败时给出具体恢复路径。

### 重置与清除

**质询：重置范围、清除筛选、清除搜索内容三者是否边界清楚？**

不清楚。当前这三个动作各自存在，但用户很难知道谁会清掉范围、谁会清掉类型、谁会保留关键词。搜索页必须避免“清除”语义过多。

**必须改变：**

- `清除搜索内容` 只清关键词和结果，不改筛选。
- 不常驻展示全局“重置”按钮；范围和类型在各自菜单中回到默认，日期在整体控件或日历中清空。
- 已有结果时，任何筛选清除都只修改统一草稿并显示取消/应用；取消恢复全部已应用值。
- 排序和分组不属于筛选清除范围；它们只改变当前加载结果的视图，可各自在选择器中回到默认。

### 页面判定

当前页面不是“完全不可用”，但它没有达到产品级搜索页标准。它更像几个已经实现的能力被垂直堆叠起来：范围控制器、搜索框、高级筛选、结果面板各自有局部合理性，但组合后没有统一规律。修复重点不是换颜色或压缩间距，而是先统一状态模型，再重排布局。

## 当前实现证据

### 页面组合

- `src/l1-entry/pages/SearchView.tsx` 依次渲染 `WorkspaceScopeController`、`GlobalSearch`、`SearchAdvancedFilters`、`SearchResults`。
- `GlobalSearch` 的 `showScopeMenu={false}`，所以截图中的范围控制来自 `WorkspaceScopeController`，不是搜索框自己的 `SearchScopeMenu`。
- 结果区的高级筛选 chips 来自 `buildSearchAdvancedFilterChips()`，不包含范围和消息类型。

### 后端搜索与本地整理

- `useSearchCommander` 调用 `fetchSearch(createSearchRequest(...))`。
- `fetchSearch` 请求 `/api/v1/search`，参数包括 `keyword`、`limit`、`offset`、`chats`、`since`、`until`、`msg_type`。
- `createSearchRequest()` 会把当前会话范围和高级筛选中的 selected chats 合并成 `chats`。
- `mapSearchAdvancedFiltersToRequest()` 只发送 `chats`、`since`、`until`。
- `sortSearchMessages()` 和 `groupSearchMessages()` 只处理当前已加载的 `results.messages`。
- 已核对本机 `E:\OneDrive - Default Directory\chatlog_alpha` 当前源码：`handleSearchCompat()` 在未传 chats 时调用 `GetSessions("", 300, 0)`，所以“全部会话”最多覆盖该调用返回的前 300 个会话，没有继续分页枚举。
- 普通关键词路径按每个会话设置有限 `fetchLimit`；数据层再从该有限消息候选中执行 literal regexp，并只匹配 `Message.PlainTextContent()`。因此日期范围内存在更多消息时，较早或候选窗口外的命中可能没有进入搜索集合。
- `total_count` 是上述已收集 `out` 的长度，再执行 offset/limit 分页；它不是独立数据库计数。在候选不完整或会话超过 300 个时，`total_count` 同样不是全库真实总数。
- 当前匹配是转义后的连续字面量，Go regexp 默认区分拉丁字母大小写。`PlainTextContent()` 会把文件标题、链接标题/描述、位置、引用和转发内容等部分结构化消息转成可读文本，但不搜索发送者名或会话名。
- 搜索响应的 `content` 并不稳定等于用于匹配的 `PlainTextContent()`；文件等消息可能返回原始结构内容，前端却只在 `message.content` 上做大小写不敏感高亮，所以可能出现后端命中但界面看不到命中位置。
- 当前前端类型只有 all/text/image/video/file，并把 file 直接映射为 49。sidecar 的 `MessageTypeShare=49` 覆盖文件、链接、小程序、视频号、引用、合并转发、笔记等多个 subtype；因此现有“文件”筛选名称与真实请求语义不一致。

结论：前端确实向后端搜索，而不是只过滤已经加载到 React 的消息；但当前后端请求也不保证覆盖全部会话和全部消息。现有 UI 的“共 n 条”和“全部命中”会过度承诺，必须在后端搜索完整性修复并通过合成数据验证后才能成立。

### 当前搜索导出能力

- 当前产品只能导出已加载结果。`useSearchWorkspaceCommander` 把 `search.results.messages` 直接传给 `createSearchExportArtifact()`；当 `loadedCount < totalCount` 时，导出任务标记为 `partial` 并明确写入“当前只导出已加载数据”。
- 当前搜索每页固定 20 条，只有用户触发“加载更多”后，新增消息才会合并进 `search.results.messages`。导出流程本身不会自动获取剩余页面。
- `/api/v1/search` 已有 `limit`、`offset`、`total_count`、`count` 字段，因此前端可以机械地循环当前端点声明的页面；但这只能取尽当前候选集合，不能修复 300 会话上限、按会话候选截断或不真实的 `total_count`。开发端点目录允许 `limit=1..500`、`offset=0..100000`，也不能据此宣称全库完整。
- 仓库中没有专用“全部命中导出”后端端点，也没有 `fetchAllSearchResultsForExport` 一类编排器。现有导出器先在前端把全部内容序列化为一个字符串，再通过 Tauri 命令一次性 `std::fs::write`；它不是流式写入。
- 因此能力判定是：132 条这类中小**端点候选集**可以通过自动分页全部取回，但在搜索完整性修复前不能称为全库“全部命中”。修复后，超大结果集若继续复用当前整字符串写入方式，仍会带来内存、冻结、取消失效和部分失败风险，需要流式或分块文件写入方案。
- 已确认产品选择：保留“全部命中”和“当前已加载”两个范围，默认选中“全部命中”。当全量路径因为安全阈值或运行时能力不可用而不能执行时，应禁用该选项并在同一位置说明原因，不能静默退化为当前已加载。

运行时限制：本次核验时 `127.0.0.1:5030` 未运行，因此确认的是当前仓库契约和打包二进制命令面，不把 `limit=500` 或 `offset=100000` 当作已完成的真实数据压力验证。

### 日期输入

- `DateInput` 是 `type="text"`、`inputMode="numeric"`、`pattern="\d{4}-\d{2}-\d{2}"`。
- 测试明确避免原生 `type="date"`，目的是统一占位格式。
- 这解决了浏览器原生日期占位不一致的问题，但没有解决用户输入体验：用户仍要手动输入 `-`，也没有自动跳到月/日字段。

## 问题清单

### P0：搜索能力真实性必须可解释

用户问“搜索内容是否真的实现，能否搜索全部信息，还是只能搜索已加载信息”。页面必须直接回答：

- 关键词、范围、类型、日期、指定会话是否发送到后端；
- 后端返回的是总命中数和分页结果；
- 当前已加载多少条，是否还有更多；
- 排序/分组到底作用于后端全量还是已加载结果。

现状只有“已加载 x / 共 y”和高级筛选说明，仍不足以避免误解。

类型同样属于真实性边界。页面不能把后端原始大类 49 命名为“文件”，也不能让 UI 类型、后端过滤、结果行图标和导出类型各自维护一套不同映射。

### P0：日期输入不能静默失败或错误归一化

当前日期输入只有格式约束，没有真实日期校验和字段级错误。必须防止：

- `2026-13-01` 被当成下一年日期；
- `2026-02-31` 通过格式检查；
- 结束日期早于开始日期；
- 用户输入一半时立即触发错误搜索；
- 空日期和非法日期都被当作“无日期筛选”。

### P1：范围与类型的控制规律不统一

范围与类型本质都是后端筛选维度，应该共享同一种规则：

- 默认值和非默认值都显示在同一个菜单触发器中，不生成额外 chip。
- 点击菜单项只更新草稿；选择“全部会话/全部类型”即回到该维度默认值。
- disabled 状态解释应靠近控件，而不是让按钮看起来像可点但无效。

### P1：范围卡片占用过多首屏空间

目前桌面上范围区域大致变成三层：

- 标题/说明/重置/设置图标；
- active chip；
- 内联范围和类型按钮。

对高频搜索任务来说，这三层应压缩为一层搜索条件栏。范围和类型各保留一个菜单触发器，日期直接编辑，不再增加 active chips 或高级设置图标。

### P1：高级筛选把不可用能力当成可见内容

“发送者筛选需要后端支持 / 收藏筛选需要后端支持 / 附件筛选需要后端支持”不应永久占据主页面，也不应换个位置继续作为 disabled 控件展示。它们属于后端能力待接入计划；实现前不进入普通用户界面。

### P1：排序/分组只整理已加载结果，容易误导

如果排序和分组只能处理当前 20 条或已加载页，它们不应放在与日期同等权重的位置。用户会以为“时间从早到晚”会对全部命中重新排序。短期应明确标注“已加载结果排序”；中期应争取后端排序和分组能力。

### P1：结果项信息不完整

搜索验收要求每条结果显示会话、发送者、时间、命中片段。当前 flat 模式下结果行主要显示 sender/time/snippet；会话信息只有按会话分组时才变成 group label。默认 flat 模式应仍能看到会话归属，否则全部会话搜索时用户不知道命中来自哪里。

### P1：当前会话不可用时的恢复路径不够强

当前会话按钮可能因为没有选中会话而 disabled。技术上有 `DisabledReason`，但截图里的主观感受是“点了不能切换”。应把“当前会话不可用”从一个小解释升级为明确行动：

- 从会话页进入搜索当前会话；
- 或保持全部会话；
- 或打开会话选择器选择一个会话。

### P2：搜索输入缺少“执行模式”提示

关键词统一由 Enter 或搜索按钮提交。已有结果后，范围、类型、日期只更新筛选草稿；页面通过“筛选尚未应用”和应用操作说明状态，不在输入框旁堆说明文字。

### P2：最近搜索与隐私模式是正确方向，但需要放入布局模型

隐私模式下最近搜索不展示，这是正确的。非隐私模式下最近搜索不应把主搜索栏继续向下推得过高；应放入搜索输入获得焦点时出现的历史建议 popover，关闭后不占页面高度。

### P2：空态应提供任务级下一步

当前空态提示“输入关键词开始搜索 / 搜索不会向后端提交空白查询”。还应在已有范围/筛选时显示：

- 当前搜索范围；
- 是否存在未完成或非法日期；
- 是否建议清除某个具体筛选；
- 若当前会话不可用，应提供“去选择会话”。

## 目标页面模型

### 桌面布局

```text
标题：搜索
副标题：检索本地聊天记录，并返回匹配消息的会话上下文。

[搜索内容输入框.............................................][搜索按钮/清除]

[全部会话 ▾] [全部类型 ▾] [日期  ____-__-__  至  ____-__-__  日历]     [草稿状态] [取消] [应用筛选]

结果工具条："发票"的搜索结果 · 已在全部会话中检索 · 当前显示 50 / 共 132 · 排序 · 分组 · 导出
结果列表：会话 / 发送者 / 时间 / 命中片段 / 跳回上下文
```

关键变化：

- 首屏只保留一个主要搜索区和一个紧凑上下文栏。
- 范围卡片不再是独立大卡片。
- 默认值和非默认值都由同一个菜单触发器表达，不再重复生成 active chip。
- 当前没有可用的额外高级筛选，因此不显示“更多筛选”入口；排序和分组回到结果工具条。
- 结果区承担“当前搜索真实状态”的解释。

### 窄屏布局

- 搜索框和 40px 图标搜索按钮保持同一行。
- 同一个条件栏重排为两层，不使用横向滚动：范围/类型/取消/应用在第一层，整体日期在第二层。
- 日历 popover 在窄屏变为贴近底部的非模态选择面板，但不覆盖状态栏，Esc/关闭后焦点返回日历按钮。
- 结果工具条折成两行；排序、分组、导出均保留明确可访问名称。
- 结果行保留 32px 的“打开上下文”箭头按钮，不用“整行可能可点”的猜测替代明确操作。

## 统一交互规则

### 范围

支持状态：

- 全部会话：默认，搜索所有后端可检索聊天记录。
- 当前会话：只有存在当前会话或 route chat 时可用。
- 指定会话：从范围菜单进入会话选择器后启用。

规则：

- 点击范围菜单项只更新 `draftFilters.scope`。
- 首次搜索时草稿与关键词一起提交；已有结果后等待“应用筛选”，不在菜单点击时请求。
- 如果当前会话不可用，按钮不只是 disabled，还提供“从会话工作台选择会话”的下一步。
- “取消”把全部筛选草稿恢复为已应用条件；清除某一条件只修改草稿，仍需搜索或应用。

### 消息类型

支持状态：

- 全部类型、文本、图片、视频、文件。

规则：

- 与范围共用同一菜单选择、草稿、取消和应用规则。
- 非默认类型直接替换触发器文本，例如 `图片 ▾`；回到“全部类型”即清除，不再出现第二套 chip。
- 若未来扩展语音、链接、位置、红包等类型，先确认 `chatlog_alpha` 的 `msg_type` 映射，再展示给用户。

### 日期

确认方案：

- 搜索页新增专用 `IntegratedDateRangeInput`；不全局替换被媒体、统计、图谱、导出复用的 `DateInput`。
- 每个日期只有一个真实 `<input>` 和一个八位数字值；视觉层把值投影到年 4 位、月 2 位、日 2 位三段横线上。
- 用户连续输入或粘贴 `20260102`、`2026-01-02`、`2026/01/02`，控件只提取前八位数字并归一为 `2026-01-02`；用户不需要输入 `-`。
- 光标、Backspace、粘贴和读屏顺序围绕一个日期整体工作，不在三个伪输入之间跳焦点。
- 完整输入后立即验证真实日期、闰年和开始/结束顺序；非法或半输入状态不发请求，并通过 `aria-invalid`、`aria-describedby` 和字段级错误说明原因。
- 同一控件提供日历按钮与快捷范围：今天、昨天、最近 7 天、最近 30 天、本月、不限日期。
- 日历选择和连续数字输入写入同一份值与同一验证函数，不能形成两套状态。

### 高级筛选

当前阶段不创建 drawer/sheet：

- 指定会话属于“范围”菜单中的会话选择流程，使用后端 `chats` 参数，不再另造高级筛选入口。
- 日期直接位于条件栏，使用后端 `since/until`。
- 排序和分组只整理已加载结果，因此只位于结果工具条；结果摘要明确“当前显示 50 / 共 132”。
- 发送者、收藏、附件没有后端能力时不显示可点击项，也不显示永久 disabled 占位。
- 当至少新增一个真实可用、又不适合条件栏的后端筛选能力时，再引入“更多筛选”轻量 popover/sheet；届时必须有应用状态、取消、Esc、焦点返回和窄屏行为。

提交规则：

- 关键词通过搜索按钮或 Enter 提交。
- 第一次搜索同时提交当前范围、类型和日期草稿。
- 已有结果后，范围、类型、日历快捷项和完整有效日期只修改草稿；点击“应用筛选”时取消旧请求并提交新快照。
- 每个日期的半输入和非法状态不触发请求；当前已应用结果保持不变，直到输入完整有效。
- 本地排序/分组立即作用于已加载结果，不伪装成全量后端重排。

## 功能完善计划

### Phase 1：搜索能力与数据边界核验

目标：先证明搜索到底覆盖什么，再设计承诺。

工作项：

- 核对 `/api/v1/search` 当前支持的 `keyword`、`chats`、`since`、`until`、`msg_type`、`limit`、`offset`。
- 用合成数据验证全部会话、当前会话、指定会话、消息类型、日期边界和分页总数，不用真实私聊内容作为测试数据。
- 明确 `total_count` 是否代表全部命中，`messages` 是否只代表当前页，加载更多是否能稳定合并同一查询。
- sender/favorite/attachment 没有后端契约时不进入普通 UI；先补能力和测试，再讨论控件。
- 将网络不可达、服务未启动、数据库未就绪、超时、参数错误和用户取消分类为不同错误模型。

验证：

- 请求 URL 与参数快照。
- 全部会话不依赖前端已加载会话列表的集成证明。
- offset/limit/total_count 连续分页测试。
- 隐私日志检查：URL、诊断事件和错误中不保留关键词或聊天内容。

### Phase 2：筛选草稿与请求状态机

目标：实现真正的“应用筛选”，统一范围、类型和日期的行为。

工作项：

- L2 建立 `draftFilters`、`appliedFilters`、`draftValidation`、`activeRequestSnapshot`、`requestStatus`。
- 首次点击搜索：校验关键词和筛选草稿，成功后一次性复制到已应用状态并请求。
- 已有结果后修改筛选：只更新草稿并显示未应用状态；点击应用后才取消旧请求并发送新请求。
- 点击取消：草稿完整恢复为已应用状态，不请求后端。
- 搜索、应用、加载更多共用请求快照与 stale response 判断，不能让旧响应覆盖新意图。
- 排序和分组从筛选模型中分离为 `loadedResultView`，即时整理当前已加载结果。
- 当前代码的 300ms 关键词自动搜索应取消；关键词改为 Enter/搜索按钮显式提交，避免与应用筛选形成两套执行规律。

验证：

- 草稿修改不触发 `fetchSearch`。
- 首次搜索同时提交草稿；再次应用只提交一次。
- 取消修改恢复全部字段。
- 非法日期、空关键词、重复点击不会发请求。
- 旧请求取消、加载更多竞态和 stale response 测试。

### Phase 3：页面布局与组件边界

目标：让首屏围绕“搜索和结果”，而不是围绕配置面板。

工作项：

- L1 `SearchView` 只组合页面标题、`GlobalSearch`、搜索专用 `SearchConditionBar`、`SearchResults` 和导出对话框。
- 搜索页停止复用三层结构的 `WorkspaceScopeController`；其他模块继续使用，不做无关全局重构。
- 删除默认展开的 `SearchAdvancedFilters` 区域；日期进入条件栏，排序/分组进入结果工具条。
- 搜索区与结果区使用连续工作面和分隔线，不使用浮动卡片套卡片。
- 桌面条件栏单行；窄屏最多两层。结果列表负责主滚动，标题与筛选不创建嵌套滚动。
- 最近搜索只在输入获得焦点且合适时显示为建议 popover，不永久增加页面高度。

验证：

- 1365x768、1440x900：搜索、条件、结果反馈同屏。
- 390x844：首条结果首屏可见；应用筛选操作不掉到孤立第三行。
- 320x800：无水平溢出，所有关键命令可达。
- 长会话名、长关键词、隐私遮罩和 200% 缩放不破坏布局。

### Phase 4：极简 UI 与元素规范

目标：用更少的视觉元素表达更清晰的操作层级。

工作项：

- 搜索：使用低对比填充输入面，保留唯一实心蓝色搜索按钮；清除为无边框图标。
- 范围/类型：无边框菜单触发器，文字和 chevron 表达可展开；选中或展开时只出现轻背景。
- 日期：每个日期一个真实输入值，视觉投影为年/月/日三段横线；连续数字、粘贴、日历和快捷日期共用同一校验器。
- 应用筛选：草稿变更后显示“筛选尚未应用”、无边框取消和无边框蓝色应用；应用中禁用重复提交。
- 排序/分组：无边框紧凑选择器；用已加载/总数摘要、tooltip 和可访问说明明确它们只整理已加载结果。
- 导出：无边框图标按钮；tooltip 和对话框说明导出范围。
- 结果行：整行可点击并支持键盘导航；只保留低对比 chevron，不再给每行增加有边框“打开上下文”按钮。
- 加载更多：无边框文字命令，加载时显示进度并禁止重复请求。
- 日期 popover、范围菜单和错误提示保留必要外轮廓；普通控件不靠边框证明自己可点。

验证：

- 每个区域最多一个实心主按钮。
- 默认态没有连续胶囊边框；hover/focus/selected/disabled 状态可区分。
- 所有图标按钮具备可访问名称、tooltip 和不小于 32px 的点击区域；窄屏关键操作不小于 40px。
- 日期合法性、粘贴、闰年和起止顺序测试。

### Phase 5：结果、导航、分页与导出

目标：让结果可判断、可继续操作，并诚实说明范围。

工作项：

- flat 结果始终显示会话名、发送者、时间和命中片段；命中高亮不改变行高。
- 结果标题显示查询词和已应用范围；摘要显示已加载数/总数，不能用草稿条件描述旧结果。
- 保留上下结果键盘导航、当前项焦点和跳回上下文。
- 打开失败区分会话未加载、会话已不存在、消息锚点缺失，并提供重新加载或打开会话的恢复路径。
- 加载更多沿用已应用请求快照；失败时保留已有结果，只在列表尾部提供重试。
- 导出面板固定提供“全部命中（总数）”与“当前已加载（加载数）”两个范围，每次打开默认选中全部命中；确认按钮随选择显示具体条数。
- 全部命中使用已应用查询快照建立独立导出任务，不把自动获取的页面写入页面结果 store，也不受用户随后编辑的筛选草稿影响。
- 全量任务按已验证的页面大小循环请求 `offset`，逐页校验查询快照、offset、total_count 和重复 ID；提供 `已获取 x / y`、取消、失败重试和结果总数变化提示。
- 中小结果集可在前端聚合后复用现有导出器；超过经压力测试确定的条数或字节阈值时，切换为 Tauri 分块写入或新增后端流式导出，不能无限构造单个大字符串。
- 当前尚未实现上述任务前，不在 UI 中把“导出”描述成“导出全部命中”。

验证：

- 全部会话 flat 结果包含会话归属。
- 上下文跳转成功、缺失锚点、会话不存在三种路径。
- 加载更多成功、失败、取消、重复点击和最后一页。
- 当前加载导出与全部命中导出范围、隐私模式、空结果和失败状态。
- 全量导出验证 0 条、1 页、跨多页、最后一页不足、重复 ID、查询变化、总数变化、取消、单页失败重试和超出安全阈值。

### Phase 6：完整状态、隐私、响应式与可访问性

目标：让页面在非成功态仍然像一个完成的产品。

工作项：

- 未开始：聚焦关键词，不提交空查询，不用大面积空态占位。
- 搜索中：保留旧结果或稳定骨架，显示取消；不清空页面制造闪烁。
- 空结果：复述已应用范围并提供清除日期、类型或切换全部会话等具体恢复动作。
- 错误：区分服务、数据库、超时和参数问题；提供重试、设置或诊断入口。
- 筛选草稿：明确未应用，不把草稿写入结果摘要；页面离开时不需要额外确认，因为没有破坏性数据。
- 隐私模式：遮罩关键词历史、会话名、发送者、命中内容、复制/导出和可访问文本中的敏感信息。
- 菜单/popover：Esc 关闭、焦点进入与返回、Tab 顺序、外部点击策略明确。

验证：

- idle/loading/ready/empty/error/cancelled/dirty-filter/privacy 全状态组件测试。
- 键盘完成搜索、修改筛选、应用、取消、结果导航和打开上下文。
- 桌面、窄屏、深色模式、200% 缩放、长文本与混合中英文截图检查。

### Phase 7：实施顺序与交付证据

目标：避免先改外观、后补状态而再次形成假完整页面。

顺序：

1. 先完成 Phase 1 的后端能力证明。
2. 再完成 Phase 2 的草稿/已应用状态和请求测试。
3. 然后改 Phase 3 页面结构与 Phase 4 元素样式。
4. 接入 Phase 5 结果行为和 Phase 6 全状态。
5. 最后运行完整前端验证、真实路由浏览器检查和截图验收。

交付证据：

- 重点单元测试：筛选状态、请求快照、日期校验、分页合并、上下文导航、导出范围。
- `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`。
- `/search` 桌面、390px、320px、空态、错误态、草稿未应用、搜索中、隐私模式截图。
- 无私密聊天内容、密钥、路径或真实搜索词进入截图与日志。

## 验收标准

### 用户任务

- 用户能在 3 秒内判断：当前搜索全部会话还是当前会话。
- 用户能从同一条件栏判断范围、类型和日期；没有后端能力的筛选不会伪装成可用控件或永久占位。
- 用户能区分正在编辑的筛选草稿和结果正在使用的已应用条件，并能应用或取消全部修改。
- 用户能一次连续输入或粘贴八位数字完成一个日期，不用手动输入 `-`，也能通过日历或快捷日期完成同一任务。
- 用户能知道搜索请求是后端检索，不是只过滤当前加载列表。
- 用户能从任意结果看到会话、发送者、时间、命中片段，并跳回上下文。
- 用户打开导出面板时默认看到“全部命中”已选中，同时仍可明确切换到“当前已加载”；两项都显示具体条数。

### 状态覆盖

- 空查询：不发送请求，提示输入关键词。
- 关键词输入中：不自动搜索，Enter/搜索按钮提交；范围、类型和日期只更新草稿，应用前不请求。
- 草稿未应用：保留旧结果与已应用摘要，显示取消和应用筛选；非法日期禁用应用。
- 搜索中：保留稳定上下文，可取消。
- 无结果：显示当前范围和筛选，并提供清除具体筛选。
- 错误：区分服务、DB、超时、参数不支持。
- 隐私模式：隐藏关键词历史、结果内容、会话敏感名，但保留结构和计数。
- 窄屏：320px 起没有横向溢出；条件栏最多两层，首条结果在 390x844 首屏可见。

### 原型验收证据

- `output/search-page-grilling-redesign.html` 可独立打开，不依赖后端和真实聊天数据。
- 1440x900 默认态：条件区 115px 高，首条结果 y=274.3，页面 `scrollWidth === clientWidth === 1440`。
- 390x844 草稿态：条件区 140px 高，结果区 y=261.6，首条结果 y=361.4，页面 `scrollWidth === clientWidth === 390`。
- 320x800 极窄检查：`scrollWidth === clientWidth === 320`。
- 统一草稿已验证：范围、九类消息多选、发送者、日期和关键词只修改草稿；单一提交动作按状态命名；取消恢复全部已应用值；pending 取消保留旧结果和脏草稿。
- 日期交互已验证：连续 8 位输入、16 位起止日期粘贴、四个快捷范围、真实换月、单日后继续选范围、反向选择自动排序、错误日期阻断提交。

## 优先级建议

1. 先证明后端检索边界，并实现草稿/已应用/请求快照状态机；这是所有布局和文案可信的前提。
2. 再收敛页面结构、范围/类型/日期规律和极简元素层级，同时完成非法日期阻断。
3. 然后补齐结果真实性、会话上下文、分页竞态、排序/分组边界和导出范围。
4. 最后覆盖空态、错误、隐私、键盘、窄屏与 200% 缩放；发送者、收藏、附件只有在后端契约完成后才进入 UI。
